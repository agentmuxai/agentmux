# Storage schema version history

**Status:** living: one entry per schema version, added in the change that bumps the constant.

What each `user_version` of the three SQLite stores added, moved here from the doc comments on the version constants in [`crates/srv/src/backend/storage/migrations.rs`](../../crates/srv/src/backend/storage/migrations.rs). The constants (`SHARED_STORE_SCHEMA_VERSION`, `OBJECT_SCHEMA_VERSION`, `IDENTITY_STORE_SCHEMA_VERSION`) stay in the code, with what a reader needs to change them safely; this file is the log of why each number exists. Add the entry for a new version here, in the same change that bumps the constant.

## Shared store (`~/.agentmux/shared/store.db`)

Stamped after `run_shared_store_schema`; versioned independently from `objects.db`.

- **v1** — initial: identity accounts/bundles/bindings/links, memory bundles, drone definitions, muxbus credentials
- **v2** — db_cron_jobs: persistent scheduled injection jobs
- **v3** — rename db_identity_accounts -> db_accounts, db_memory_bundles -> db_bundles (SPEC_PRESET_TO_BUNDLE_REFACTOR_2026_07_02.md Phase 4a, SPEC_ARMORY_PHASE4_STORAGE_RENAME_COMPLETION_2026_07_12.md)
- **v4** — db_agent_credentials: per-agent M2M Cognito client_id/secret + cached access token, one row per locally-registered agent_id, so cloud_subscriber's /reactive/* calls use a credential bound to the agent, not the shared per-account MUXBUS_TOKEN
- **v5** — db_cron_jobs.max_age_secs: optional hard expiry (seconds since created_at) beside max_fires; NULL = no expiry (docs/specs/SPEC_AGENT_POLLING_AND_WAKEUP_HARDENING_2026_08_04.md Phase 0)
- **v6** — db_agent_native_memory: durable mirror of each agent's native memory files, keyed by (agent_id, filename) (docs/specs/SPEC_NATIVE_MEMORY_DURABLE_SYNC_2026_08_07.md)
- **v7** — db_bundles.instructions_by_provider: JSON {provider_id: content} variants, additive to the flat `instructions` column (ABF v0.2 §2.2, docs/specs/SPEC_ABF_V0_2_PROVIDER_AWARE_COMPONENTS_AND_NATIVE_MEMORY_2026_08_10.md)
- **v8** — db_agent_native_memory_versions: append-only history, one row per `agent:memory:write_file` call (plus reverts and, later, out-of-band-write detection); the v6 mirror only holds the current value (docs/specs/SPEC_MEMORY_VERSION_CONTROL_AND_ARMORY_AUDIT_2026_08_19.md)
- **v9** — db_bundles.is_system: schema parity with objects.db v27 (the AgentMux-controlled Global Bundle tier)
- **v10** — db_bundle_versions: append-only Global Memory entry history, schema parity with objects.db v35 (SPEC_AGENT_FACING_GLOBAL_MEMORY_API_2026_09_15.md)
- **v11** — db_cron_jobs.target_uid: the target agent's UID (`db_agents.id`) beside the slug column, resolved once at create time and dual-written; nothing reads it yet, a job still fires by `target`. Non-interactive ingress never resolves a name at fire time, so the UID is captured while a human or model is present; empty when the name did not resolve, never guessed (identity M1b, SPEC_AGENT_IDENTITY_CARRIED_NOT_DERIVED_2026_09_23.md §5.4, §9.1)
- **v12** — db_cron_jobs.created_by_uid and db_bundle_versions.written_by_uid: the actor's UID beside each actor-name column, from the request's `Caller` (its `X-Agent-Token`), never a body field; empty for an Unattributed request, never guessed. Dual-written, not yet read (identity M4c-1, SPEC_AGENT_IDENTITY_CARRIED_NOT_DERIVED_2026_09_23.md §6.5.9)

## Objects store (`objects.db`)

Stamped after `run_object_schema`. The flat schema reset the counter to 1 (the pre-flatten chain never set `user_version`, so legacy files read 0). Bumped per additive migration.

- **v1** — flat schema baseline
- **v2** — db_agent_definitions.updated_at
- **v3** — db_agent_definitions.user_hidden (Phase 2 hide templates, SPEC_AGENT_PICKER_TWO_TIER_2026_05_24.md Q2 Decision Y)
- **v4** — db_agents consolidation table (Phase 3a: every definition/instance write dual-writes here). Reads moved over piecemeal: the instance side in Phase 3b (#3080), every `agent_def_*` method in Phase 3d (#3092, v31); both legacy tables were dropped in v32
- **v5** — db_agents.last_block_id (Phase 3c; the latest launch's block, so the consolidated read finds the session snapshot without joining db_agent_instances)
- **v6** — container_image / container_volumes / container_name on db_agent_definitions and db_agents (SPEC_CONTAINER_PANE_SUPPORT_2026_06_11.md Phase 0; host agents default to '' / '[]' / '')
- **v7** — db_muxbus_credentials: global singleton for MuxBus cloud Cognito PKCE tokens (access, refresh, id) + expiry + user email
- **v8** — db_memory_bundles.is_global: global-tier flag for Armory bundles injected into every agent's CLAUDE.md at launch
- **v9** — db_memory_bundles.sort_order: explicit order of the Armory global bundles (the CLAUDE.md injection order); existing rows default to 0, the Armory Global section assigns positions via reorder
- **v10** — db_skills, db_mcp_servers, db_agent_skills_ref, db_agent_mcp_ref: standalone MCP Server and Skill primitives with per-agent ref tables (SPEC_V1_MCP_SKILLS_PRIMITIVES_2026_06_30.md)
- **v11** — rename db_identity_accounts -> db_accounts, db_memory_bundles -> db_bundles (SPEC_PRESET_TO_BUNDLE_REFACTOR_2026_07_02.md Phase 4a, SPEC_ARMORY_PHASE4_STORAGE_RENAME_COMPLETION_2026_07_12.md)
- **v12** — use_ambient_login on db_agent_definitions and db_agents: per-agent opt-in to the CLI's global (ambient) login when no oauth-class account resolves at spawn (SPEC_ACCOUNT_DELETE_DEAUTH_LAYERS_2_4_2026_07_14.md §2.3, layer 3). Defaults to 0 (fail by default); a since-retired data migration set it to 1 for pre-existing linkless agents
- **v13** — db_agent_credentials: per-agent M2M muxbus credential, mirroring db_muxbus_credentials in both schemas: id_store falls back to this per-channel schema on installs that haven't applied 0011_shared_store_backfill, so cloud_subscriber must not assume the shared-schema copy (v4 there) is in use
- **v14** — db_agent_native_memory: durable mirror of each agent's native memory files, keyed by (agent_id, filename); duplicated in both schemas for the same id_store fallback reason as v13 (docs/specs/SPEC_NATIVE_MEMORY_DURABLE_SYNC_2026_08_07.md)
- **v15** — model_vendor_base_url on db_agent_definitions and db_agents: points a harness (CLI) at a non-default model vendor backend (e.g. ANTHROPIC_BASE_URL for a claude-provider agent), the data side of treating harness and model vendor as distinct. Defaults to '' (the harness's default vendor); settable only via `agent.define`, validated against the provider's `ProviderConfig::base_url_env_var`
- **v16** — db_bundles.instructions_by_provider: JSON {provider_id: content} variants, additive to the flat `instructions` column (which stays "default") (docs/specs/SPEC_ABF_V0_2_PROVIDER_AWARE_COMPONENTS_AND_NATIVE_MEMORY_2026_08_10.md §2.2). Defaults to '{}'. Delivering a variant into a running agent is out of scope (that spec's non-goals): the column only makes the data storable, exportable and importable
- **v17** — auto_continue_enabled on db_agent_definitions and db_agents: the Warden Supervisor's per-agent auto-continue opt-in (default 0). RETIRED with the Warden Supervisor: nothing reads or writes it. It stays because older builds sharing the data dir still select it (docs/analysis/ANALYSIS_WARDEN_AUTO_CONTROLLER_CONTINUATION_WATCHER_2026_08_12.md)
- **v18** — db_agent_jekt_keys: per-agent HMAC-SHA256 signing key for host-tier jekt sender verification. One row per agent_id, minted on first use and injected only into that agent's own MCP server env (AGENTMUX_JEKT_KEY), so a signature can only be produced by the agent it claims to be from (docs/specs/SPEC_JEKT_TRUST_LAYER_COMPLETION_2026_08_13.md §2.2)
- **v19** — db_agent_definitions.memory_id: the agent's own dedicated ABF bundle, set once at creation and never updated (agent_def_update's SET clause omits it, like is_seeded/slug/parent_id). Distinct from db_agent_instances.memory_id (a launch's bundle, which may diverge). Mirrored into db_agents as a SEPARATE default_memory_id column, because db_agents.memory_id is instance-only by convention (see db_agents' CREATE TABLE comment). Defaults to ''; the m0021 migration backfills every unbound definition with a fresh bundle (ARCHITECTURE_MANDATORY_ABF_RETHINK_2026_08_14.md §3.1)
- **v20** — db_agent_lan_keys: per-agent Ed25519 keypair for LAN-tier jekt sender verification, mirroring v18 but asymmetric: LAN is multi-party, so a receiving peer must verify without being able to forge. public_key is distributed to LAN peers on demand (not secret); private_key goes only to that agent (its MCP config's AGENTMUX_LAN_KEY and its own token-authenticated key fetch) (docs/specs/SPEC_JEKT_LAN_TIER_SIGNING_2026_08_15.md §2.1)
- **v21** — db_lan_peer_pubkey_pins: trust-on-first-use pin of a REMOTE agent_id's LAN public key as first seen from mDNS-discovered peers (#2588). Discovery is unauthenticated: any device can announce an agent under an existing name, so trusting whichever peer answers first lets an attacker's self-minted key be accepted for a victim's agent_id. Pinning the first-seen key and rejecting a later mismatch is the SSH-host-key mitigation for "no PKI available"; it narrows the spoofable case to a race on the first lookup (docs/specs/SPEC_JEKT_LAN_TIER_SIGNING_2026_08_15.md §2.2)
- **v22** — db_background_tasks: durable record of a declared long-running (`run_in_background: true`) task attached to a block, so its liveness survives `DockSnapshotCache`'s 1-hour eviction and a session reconnect/reload; the client-transcript-derived signal had no durable source of truth. Per-channel (block ids mean something only within their channel), not the shared store. Renumbered from v20 after merging with the LAN-tier signing PR, which claimed v20/v21 independently (docs/status/STATUS_ATTACHED_TASK_AXIS_AND_DEV_LOOP_2026_08_15.md, #2492)
- **v23** — db_bundle_skills_ref, db_bundle_mcp_ref: bundle-level references to the standalone skill/MCP-server primitives, mirroring v10's agent-level ref tables but keyed by bundle_id: composable model v2, step 1 (docs/specs/SPEC_BUNDLE_AS_CONTAINER_V2_2026_08_17.md, #2024 item 3). A bundle's mcp_servers/skills JSON columns are untouched (still the .abf export/import format); these tables are the live-resolution path. Deliberately NO FK to db_bundles (unlike the agent-level tables' FK to db_agent_definitions); see their CREATE TABLE comment
- **v24** — db_agent_native_memory_versions: append-only version history for native memory content, duplicated across schemas like the v14 table (id_store per-channel fallback) (docs/specs/SPEC_MEMORY_VERSION_CONTROL_AND_ARMORY_AUDIT_2026_08_19.md)
- **v25** — db_agent_groups: saved, named target sets for fleet control (broadcast/bulk-stop across many agent panes; docs/specs/SPEC_MULTI_AGENT_FLEET_CONTROL_2026_08_20.md): a durable list of block ids under a name, since a saved group scales as a fleet grows where a raw ephemeral selection doesn't. Per-channel (block ids), not the shared store. Renumbered from v24 after colliding with the native-memory-version PR (the same collision class as v20 to v22)
- **v26** — db_agent_definitions.conversation_visibility (TEXT, default 'private') + db_conversation_trust_grants: `muxspect` Phase B/C's per-agent disclosure policy for an incoming cross-tier `transcript_request` jekt (docs/specs/SPEC_MUXSPECT_CROSS_TIER_CONVERSATION_VISIBILITY_2026_08_21.md; tier rules in docs/specs/SPEC_JEKT_TRANSCRIPT_REQUEST_TIER_RULES_2026_08_22.md). One of "private" (auto-deny), "trusted_peers" (auto-approve an allow-listed requester), "ask" (force human escalation). Also dual-written to `db_agents`, like `auto_continue_enabled` (a simple per-agent setting, unlike `memory_id`/`model_vendor_base_url`, which use a differently-named column there). Deliberately NOT in `DefinitionRecordV1`'s cross-channel wire format: channel-local, so a cross-channel-reopened agent starts at "private". `db_conversation_trust_grants` mirrors `db_lan_peer_pubkey_pins`' shape (own module, get/set methods, case-insensitive agent_id lookups)
- **v27** — db_bundles.is_system: an AgentMux-controlled, highest-priority Global Bundle tier (INTEGER, default 0). A system row is always also is_global=1 (enforced in code, not a CHECK; see `bundle_upsert_system`). Writable only through the `upsertsystemmemory`/`deletesystemmemory` RPCs and `Store::bundle_upsert_system`/`_delete_system`; the generic `bundle_upsert`/`_delete`/`_reorder` refuse an is_system=1 row. Injected first in `format_global_bundle_block`'s output, wrapped in explicit override wording, ahead of every ordinary Global Bundle section (docs/specs/SPEC_GLOBAL_MEMORY_SYSTEM_TIER_2026_08_24.md)
- **v28** — db_agent_activity_summaries: one-shot, on-demand Haiku-generated activity summary per `definition_id`, the AgentPicker's "My Agents" conversation-preview fallback for legacy rows with no structured `output.state.json` snapshot (see `has_snapshot` in `listrecentsessions`, `agent_handlers/session.rs`). Generated from the instance's raw `"output"` filestore file through the shared Ambient Model Call gateway (`invoke_haiku`, docs/specs/SPEC_AMBIENT_MODEL_CALLS_FRAMEWORK_2026_07_03.md), lazily (first picker load that needs it) and cached forever once non-empty, like `SubAgent.display_name`, not `term:ambient_summary`'s per-turn refresh. Renumbered from v27 after colliding with the system-tier PR (#2782) (docs/reports/REPORT_AGENT_PICKER_FIELD_ORDER_SORT_AND_DATA_GAPS_AUDIT_2026_08_24.md §5a)
- **v29** — db_agents.session_id / status / started_at / ended_at: the agent's LATEST launch state, the four `db_agent_instances` columns the consolidated row never got (Phase 3a left them "on the block", but the recent-sessions picker, the pane close/reopen write-back and the status-filtered instance list kept reading the legacy table, which is why it could not be dropped). One row per agent means one launch state per agent; a continuation moves it to the new block/session. Backfilled by `m0025_agents_launch_state_backfill` (latest instance per projection key) and kept current by the instance dual-write; the Phase 3b read flip (SPEC_AGENT_ARCHITECTURE_2026_05_27.md) retires the legacy reads on top of it. No unique index on `db_agents(slug)`: template-launch projections copy their template's slug, so uniqueness stays a definition-level rule enforced by the slug collision scan in `agent_def_insert`
- **v30** — `db_agent_content` / `db_agent_skills` / `db_agent_history` / `db_agent_identity_links` / `db_agent_skills_ref` / `db_agent_mcp_ref`: `agent_id`'s foreign key now targets `db_agents(id)`, not `db_agent_definitions(id)`. Existing rows already satisfy it (each `agent_id` is a definition id with a `db_agents` mirror at the same id); what changes is that a `db_agents` row with no definition counterpart (a template launch) can now hold these directly, closing the gap `listrecentsessions`' template fallback (Phase 3b, #3080) exists for. SQLite can't redefine an FK in place, so `m0028_agent_child_tables_repoint_fk` rebuilds the six tables (rename, recreate, copy, drop, `PRAGMA foreign_key_check` before commit); a fresh install gets the new FK from the CREATE TABLE statements in `object_schema.rs` (Phase 3c, SPEC_AGENT_ARCHITECTURE_2026_05_27.md)
- **v31** — No DDL change. Every `agent_def_*` write now lands on `db_agents` only (Phase 3d, #3092); `db_agent_definitions` is no longer kept in sync. Bumped anyway: `check_schema_compat` is a downgrade guard as much as a schema guard, and this release changes what a NEWER binary's writes mean to an OLDER one. Without the bump, rolling back one binary would silently accept a store where new agents exist only in `db_agents`, and that binary's `agent_def_get`/`update`/`delete` (still on `db_agent_definitions`) would 404 or replay stale legacy values into `db_agents` on edit. Stamping 31 makes that downgrade refuse to open
- **v32** — `db_agent_definitions` and `db_agent_instances` are dropped (Phase 3e, SPEC_AGENT_ARCHITECTURE_2026_05_27.md, closing out the tracking spec): nothing has read or written either since v31 (the definition and instance flips, #3080/#3092). Their `CREATE TABLE`s and indexes are gone from this function, because migrations run before it on every boot and leaving them would recreate empty tables after the drop. `db_agent_definitions`' `ALTER TABLE ADD COLUMN` entries are KEPT, gated on the table still existing (see `add_legacy_definition_columns` in `object_schema.rs`): several pending migrations (m0007, m0025, m0026, m0028) call `Store::open()`, running this function, before m0029 drops the table in the same upgrade pass, and an old store missing one of those columns would fail their reads with "no such column" (#3096). An existing store's tables are removed by `m0029_drop_legacy_agent_tables`; a fresh install never has them. `adopt_legacy_table_names`' `db_forge_agents` → `db_agent_definitions` rename stays on purpose: an install old enough to carry `db_forge_agents` reaches it in an EARLIER migration's `Store::open()`, so the rename still fires before m0029 drops what it produced, and no data is stranded under the old name
- **v33** — `db_agent_project_instructions`: what each agent was last observed to read as project instructions from its working directory, keyed `(agent_id, path)` (Phase 3 of SPEC_INSTRUCTION_AND_MEMORY_PORTABILITY_2026_09_09.md). Records a content hash and an observation time, never the content: a tracking table, not a mirror. Unlike `db_agent_native_memory`, which keeps content because it is a durable copy of files AgentMux may have to serve when the originals are unreachable, these files belong to the repository, are always readable from it and are never written by AgentMux; storing them would make a second copy of somebody else's file with no one to keep it honest. Purely additive: nothing reads it at launch, and an agent with no row has no prior observation to compare against
- **v34** — `db_agent_skills_ref` / `db_agent_mcp_ref` / `db_bundle_skills_ref` / `db_bundle_mcp_ref` drop their `skill_id` / `mcp_id` FK to this store's LOCAL `db_skills` / `db_mcp_servers` (Phase 2 of SPEC_DURABLE_BINDINGS_2026_09_10.md §5.4, #3182). Once catalog writes redirect to `identity_store`, the local catalog copies stop gaining rows, so binding a post-redirect skill/server would hit `FOREIGN KEY constraint failed` (`PRAGMA foreign_keys=ON` in production, see `Store::configure_and_migrate`). The `agent_id → db_agents` FK on the agent-level pair stays; existence moves to the application layer (`managed_bind_agent` / `managed_bind_bundle`'s `catalog: &Store` check), as `db_bundle_skills_ref` / `db_bundle_mcp_ref` already did for `db_bundles` (see their CREATE TABLE comment in `object_schema.rs`). SQLite can't drop a constraint in place, so `m0032_drop_catalog_fk_from_ref_tables` rebuilds an existing store's four tables; a fresh install gets the trimmed FK from the CREATE TABLE statements in `object_schema.rs`
- **v35** — db_bundle_versions: append-only version history for Global Memory entry content (`name` + `instructions`), one row per write through the agent-facing Global Memory API (docs/specs/SPEC_AGENT_FACING_GLOBAL_MEMORY_API_2026_09_15.md Phase 0). Same shape as `db_agent_native_memory_versions`, keyed by a single `bundle_id` instead of `(agent_id, filename)`. Global Memory (`db_bundles`) had no audit trail, only `updated_at`, and is about to gain a write path an agent (not just a human in the Armory UI) can reach. `written_by` is a TRUSTED identity column (an agent's real `AGENTMUX_AGENT_ID`, or `"armory-ui"`), kept separate from the caller-describable `source` / `source_detail` pair, which would let an agent claim `source: "human"` with nothing to contradict it (#3237)
- **v36** — db_agent_wan_keys: per-agent Ed25519 keypair for agent-to-agent WAN-tier jekt signing (#2586, second half). Mirrors v20's shape but is a SEPARATE keypair from `db_agent_lan_keys`: LAN public keys are permanently TOFU-pinned by peers (v21), so they cannot rotate (SPEC_JEKT_HOST_KEY_TTL_ROTATION_2026_09_14.md §4), while WAN keys are served from muxbus's ownership registry and are meant to; one key cannot have both lifecycles. `key_version` is reserved for the publish-sync and rotation phases (that spec's §3.2/§3.6) and unread so far
- **v37** — db_agent_tokens: per-agent local identity token, keyed by the agent's UID (`db_agents.id`) — identity M1 of `SPEC_AGENT_IDENTITY_CARRIED_NOT_DERIVED_2026_09_23.md` (§6, §9.1). Minted on first spawn (`agent_token_ensure`), injected into that one agent's process env as `AGENTMUX_AGENT_TOKEN`, revoked on delete via `purge_agent_dependents`. Unlike v18's jekt key and the registry entry files, which are keyed by display name and so are shared by two same-named agents (spec §6.3), this is keyed by a `PRIMARY KEY` that is a UUID for every non-template row. Read since M4: it identifies a request's Caller (host-tier sender verification, the agent's own key fetch). See `storage/agent_tokens.rs`.
- **v38** — db_agent_key_tombstones: the lowercased names (slug, display name, instance name) of every deleted agent — identity M4a of `SPEC_AGENT_IDENTITY_CARRIED_NOT_DERIVED_2026_09_23.md` §6.5.4. Signing keys are keyed by name, so a later agent that takes a deleted agent's name would inherit its keys; M4d copies name-keyed keys to UIDs and must never copy a tombstoned name's. Written from M4a on, before any copy exists, so the record is complete when M4d reads it. Written only — nothing reads it until M4d.
- **v39** — db_bundle_versions.written_by_uid: the writer's UID beside the `written_by` name, taken from the request's `Caller` (its `X-Agent-Token`), never from a body field; empty for an Unattributed write, the Armory UI and the seeders. Dual-written, not yet read. Not only parity with the shared store: when that store is unavailable `id_store` falls back to this one and writes here. Identity M4c-1 of `SPEC_AGENT_IDENTITY_CARRIED_NOT_DERIVED_2026_09_23.md` §6.5.9.
- **v40** — db_jekt_held: a jekt to a known agent of this channel that no delivery tier could take (the agent was not running anywhere), held for up to 24 h and replayed when it registers, with the trust verdicts it was accepted with as explicit columns. `SPEC_DURABLE_JEKT_DELIVERY_2026_09_24.md` Phase 1.
- **v41** — db_background_tasks.owner_tool_use_id: the `tool_use_id` of the Agent call whose subagent launched this background task (the `parent_tool_use_id` on the stream line that issued the Bash call); NULL for the agent's own tasks. Joins a task to its subagent, whose `meta.json` records the same id. Phase 2 of `SPEC_BACKGROUND_TASK_STRUCTURED_FEED_AND_SWARM_OWNERSHIP_2026_09_27.md`.
- **v42** — db_agents.last_runtime: the Runtime menu choices (permission mode, model, effort) the user last made for this agent, as a JSON object, '' when none. Lets Continue / Reattach / a fresh open start where the user left off instead of on the definition's defaults. Written only when the user picked something. Item 2 of `SPEC_RUNTIME_MENU_REMAINING_GAPS_2026_10_01.md`.
- **v43** — db_viewer_devices: the devices paired with this channel's viewer listener, each with the SHA-256 of its viewer token (never the token), its name, its optional public key and when it was paired and last seen; plus db_agents.hide_from_devices, an agent's opt-out from the viewer routes. agentmux-mobile's SPEC_AGENT_STATUS_AND_LIVE_PANE_FEED_2026_10_07 §13.2, §4.3. See `storage/viewer_devices.rs`.
- **v44** — db_mcp_server_reach: per catalog MCP server, whether it reaches every agent (`all_agents`) and whether container agents get it too (`in_containers`). A table of its own beside `db_mcp_servers`, so nothing that copies catalog rows changes. Both default 0: a catalog server reaches only the agents it is bound to. `SPEC_CONNECTORS_MCP_WHAT_AGENTS_RUN_2026_10_10.md` §2.1.
- **v45** — db_lan_pin_installs: the install whose certificate vouched for a LAN name pin's key (instance id and host hint), kept beside the pin so a key moves only on that install's say; and db_lan_retired_keys: the fingerprints a name has moved off, with when and by whom, so a message signed with one is refused as retired. Tables of their own beside `db_lan_peer_pubkey_pins`, so that table's rows and readers are unchanged. See `storage/lan_peer_pin_installs.rs`.

## Identity store (`~/.agentmux/shared/identity-store.db`)

A different file from `store.db`, stamped after `run_identity_store_schema`, with a counter independent of `SHARED_STORE_SCHEMA_VERSION`. The rule for when a change does not bump it is on `IDENTITY_STORE_SCHEMA_VERSION` in the code.

- **v1** — initial: agent→account links, bundles, drone definitions, muxbus credentials, per-agent M2M credentials, native memory mirror, cron jobs: everything `run_shared_store_schema` held EXCEPT `db_accounts` (docs/specs/SPEC_IDENTITY_STORE_SPLIT_2026_08_17.md §3.1)
- **v2** — db_accounts, as a FALLBACK MIRROR only (#2632): a link resolves via this store, but the account row it points to could exist only in the per-channel-isolatable `id_store`, empty on a fresh channel, so the bug wasn't fixed end to end without it. `id_store` stays the PRIMARY, authoritative write path (Armory's disposable-test-account isolation is unchanged); this copy is consulted only when `id_store` lacks the row (see `identity::resolver::inject`'s account resolution: read-with-fallback plus write-back to the source store)
- **v3** — db_agent_native_memory_versions, for parity with the v1 native memory mirror this store carries. Not an actively written duplicate either (`id_store` / `store.db` stay authoritative, see v2); it is here so a future always-global read path, like v2's for db_accounts, isn't blocked on a missing table (docs/specs/SPEC_MEMORY_VERSION_CONTROL_AND_ARMORY_AUDIT_2026_08_19.md)
- **v4** — db_bundles.is_system, for parity with OBJECT_SCHEMA_VERSION v27 / SHARED_STORE_SCHEMA_VERSION v9 (same reasoning as v3: not an actively written duplicate). A real ALTER TABLE ADD COLUMN in `run_identity_store_schema`, so the counter MUST bump with it: an unbumped counter leaves an existing identity-store.db at the old `user_version` forever, defeating `check_schema_compat` / `stamp_version`'s forward-compat lock for this store (#2782; docs/specs/SPEC_GLOBAL_MEMORY_SYSTEM_TIER_2026_08_24.md)
- **v5** — `db_work_queue`, the Muxqueue backlog (docs/reports/REPORT_UNIVERSAL_AGENT_WORK_QUEUE_2026_09_01.md). A new table, no ALTER, but the counter still bumps: an identity-store.db stamped v4 that a v5 binary opens must read as older, not "already current" (the #2782 reasoning of v4). Deliberately in THIS store, not the per-channel one: a queue with per-channel rows means "any agent IN THIS CHANNEL can pick it up", close to useless when every local/dev/portable build is its own channel (the report's §6.2; docs/analysis/ANALYSIS_PER_CHANNEL_AUTH_BYPASSES_2026_08_31.md for what the per-channel/global seam has already cost)
- **v6** — `db_skills`, `db_mcp_servers` (Phase 2 of SPEC_DURABLE_BINDINGS_2026_09_10.md): the AUTHORITATIVE catalogs from this version. The per-channel copies in `run_object_schema` keep their declarations (never removed; that spec's §5.1 and §8 item 3) and remain only the best-effort degraded-mode fallback `bootstrap/stores.rs` substitutes (`mstore` for `identity_store`) when the identity store can't be resolved, created or opened. NOT declared here with the ref tables (`db_agent_skills_ref`, `db_bundle_skills_ref` and the MCP equivalents): those stay channel-scoped until Phase 3/6 promotes them, and adding them unpaired with a live writer would be schema for a phase that hasn't shipped
- **v7** — partial UNIQUE indexes on `db_skills(name, skill_type)` and `db_mcp_servers(name)`, each `WHERE is_global = 1`: global rows only, so two owners' private rows may share a name. Closes a race in `m0031_carry_skills_and_mcp_servers_to_identity_store`: two channels' migrations can run concurrently (several AgentMux instances is a supported scenario), both read "no matching global row yet" and insert under different ids, and the first-wins cross-channel dedup fails without a DB-level constraint to arbitrate (#3181). The migration's insert now handles the resulting `UNIQUE constraint failed` by re-querying for the winning row
- **v8** — `idx_ids_skills_global_name` replaces `idx_ids_skills_global_name_type`: the skill global-uniqueness index narrows from `(name, skill_type)` to `name`, matching the invariant `skill_upsert_unique_global`'s dup-check enforces (`WHERE name = ?1 AND id <> ?2 AND is_global = 1`, no `skill_type` filter). The v7 index was narrower than that invariant, so a same-name, different-`skill_type` race between two channels could insert two rows the application treats as duplicates (#3182, SPEC_DURABLE_BINDINGS_2026_09_10.md §5.4). MCP servers don't have the mismatch (`idx_ids_mcp_servers_global_name` is already name-only), so this bump is skills-only. `m0033_narrow_skill_global_uniqueness_index` collapses any same-name/different-type pair that `m0031`'s `(name, skill_type)` dedup may have produced, keeping the earlier-`created_at` row, before the new index is created
- **v9** — db_bundle_versions, for parity with OBJECT_SCHEMA_VERSION v35 / SHARED_STORE_SCHEMA_VERSION v10 (same reasoning as v3; docs/specs/SPEC_AGENT_FACING_GLOBAL_MEMORY_API_2026_09_15.md)
