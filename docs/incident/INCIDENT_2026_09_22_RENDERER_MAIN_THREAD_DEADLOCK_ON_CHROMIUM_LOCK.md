# INCIDENT 2026-09-22 — v0.56.12 main window froze permanently: renderer main thread deadlocked on a Chromium-internal lock

**Status:** historical — incident record. Root cause named (§3a) after the local build tree's matching PDB was found; the one-line build fix is in `scripts/cef-build/args-windows.gn` (same change set as this doc) but needs a Windows CEF rebuild and a new `agentmuxai/cef` release before any shipped runtime is fixed. The detection/recovery follow-ups in §7 remain proposals.
**Date:** 2026-09-22 (host local, UTC−7); freeze at 22:42:05, recovered 23:10 by killing one process.
**Author:** Agent3 (Claude Fable 5.1), investigating live from the 0.56.11 instance on the same host.
**Severity:** High. Whole main window unresponsive, never recovers on its own. First occurrence the operator has seen in months of daily use.
**Affected:** v0.56.12 portable (`agentmux-0.56.12+gc67619315`), channel `local-main-b28b7a-9c23b2f0`, host pid 53396, srv pid 53316, renderer pid 52384. CEF fork runtime `libcef.dll` 152.0.7977.83 (build timestamp 2026-09-02, identical binary shipped in 0.56.10, 0.56.11 and 0.56.12).
**Related:** `INCIDENT_2026_09_07_BACKEND_UPTIME_TIMER_FROZEN.md` (same user-visible signature, different cause — srv-side that time; renderer-side this time), `docs/status/STATUS_CROSS_CHANNEL_AGENT_OPEN_FULL_APP_FREEZE_2026_08_22.md` (not this: that one recovered after minutes).
**Evidence retained (not in repo, on host `narko`):** `~/.agentmux/agents/agent3-0630k/scratch/renderer-52384-frozen.dmp` (682 MB full dump of the frozen renderer, taken before the kill), `stack-52384.txt`, `stack-28648.txt`, `stack-53396.txt`, `stack-47672.txt` (cdb `~*k` snapshots of the renderer, a pool renderer, the browser process and the GPU process while frozen).

---

## 1. One-paragraph summary

At 22:42:05 the main window's renderer process (pid 52384) stopped executing JavaScript: its main thread blocked in `RtlAcquireSRWLockExclusive` on one process-global `base::Lock` inside `libcef.dll`, and within seconds the Compositor thread, the Chrome_ChildIOThread, the HangWatcher thread, the ThreadPoolServiceThread and a newly created AudioOutputDevice thread all queued on the same lock through the same call site. No thread in the process held it: every remaining thread was parked in its ordinary idle wait. The lock word read locked-with-waiters and no shared owner, so the owner had either exited without releasing or the word was corrupted. That is a bug in native Chromium/CEF code, not in AgentMux's frontend or backend. Everything else stayed healthy, which is why the freeze looked total while every health signal was green: the browser process still pumped messages (Windows reported it Responding), srv answered HTTP in under 2 ms, the three hidden pool-window renderers answered DevTools in 5 ms, and the launcher's UI-liveness probe (which asks the browser UI thread, not the renderer) kept passing. The only automatic symptom was srv logging `ws egress lane full … consumer stalled, dropping event` once per second from 22:46:48, because the frontend had stopped reading its socket. Nothing in the product detects a hung renderer, so the window stayed dead for 28 minutes until the process was killed by hand, after which the host's existing crash-recovery page appeared and Reload restored the session with no data loss.

## 3. How the diagnosis was narrowed (so it can be repeated)

1. **Process table.** All 0.56.12 processes alive; Windows `Responding=True` for every one; host main thread idle in a user wait; srv 10 s total CPU. Rules out a spinning main thread, a hung message pump, and a busy backend.
2. **srv health.** `/` answers in 1.5 ms; srv log shows only the egress-lane warning. Same signature as the 2026-09-07 incident, whose §0 correction warns that "consumer stalled" cannot tell a client that stopped reading from a server task that stopped writing.
3. **Renderer liveness over DevTools.** The host exposes `--remote-debugging-port=57249`. `Runtime.evaluate` on the three pool pages answered in 5 ms; on the main page it never answered (8 s timeout), and `Network.enable` never acked. That is the decisive split: only the main window's renderer is dead.
4. **Not a hidden modal.** `EnumWindows` over the host's windows: the main HWND is visible and enabled; no dialog HWND exists. Chromium's JS-dialog path is ruled out.
5. **Thread stacks (cdb non-invasive, `-pv`).** In pid 52384: `CrRendererMain` is 26 frames deep in `ntdll!RtlpAcquireSRWLockExclusiveContended` reached from the task-running machinery (no Blink/V8 frames above it — the block happened in per-task bookkeeping, not in page code). HangWatcher, ThreadPoolServiceThread, Chrome_ChildIOThread, Compositor and AudioOutputDevice are in the identical three-frame lock sequence (`libcef+0x233d8ba ← +0x2334269 ← +0x2443e13` or `+0x244402e`). All 31 foreground pool workers, both background workers, both single-thread pool threads, Font thread, LoaderLockSampler and PerfettoTrace are in their standard idle waits, byte-identical stacks. Renderer 28648 (a pool window) has its main thread in the ordinary idle `WaitForSingleObjectEx` of the default message pump, confirming what "idle" looks like in this binary.
6. **The lock itself.** Saved registers at the contended frame give the lock pointer: `rcx = r14 = 0x7ffdaf256b38` in the main, Compositor and audio threads — one lock. `!address` places it in `libcef.dll`'s writable image data (RVA `0x11656b38`), so it is a process-global, not a heap object. Lock word `0x000000ed1e2ff413`: bit0 Locked, bit1 Waiting, bit3 MultipleShared clear; the pointer part is the HangWatcher thread's wait block, whose `Back` link is the Compositor's. An SRW lock records no owner, and no live thread is inside a critical section, hence "abandoned or corrupted".
7. **Symbols.** The fork's `libcef.dll` (`agentmuxai/cef`, release `cef-windows-x86_64-152.0.7977.83`) ships no PDB and the fork publishes none. Upstream CEF 152.0.6 symbols (same Chromium 152.0.7977.83) were downloaded and tried with `SYMOPT_LOAD_ANYTHING`: the export-address deltas between the two binaries range from `+0x91430` to `−0x3c93200`, i.e. a different link order, so every name they produced was garbage (an idle pump resolved to FedCM account-fetcher code) and was discarded. The matching PDB was then found on the build machine itself: `~/cef-build/chromium_git/chromium/src/out/Release_GN_152/libcef.dll` is byte-identical to the shipped DLL and `libcef.dll.pdb` (5.4 GB) beside it loads against the dump with no mismatch. Everything in §3a comes from that.

## 3a. Root cause, named

With real symbols the six waiting threads and the lock resolve as follows (dump `renderer-52384-frozen.dmp`, cdb, `~*k`):

- **The lock** at `libcef+0x11656b38` is `base::internal::InstanceTracer`'s global storage mutex (`ln` → `InstanceTracer::counter_+0x8`, i.e. the `std::mutex` returned by `GetStorageMutex()` in `//base/allocator/partition_allocator/src/partition_alloc/pointers/instance_tracer.cc`). It is a plain non-recursive `std::mutex`, which on Windows is an SRW lock — hence the raw stacks.
- **What the tracer is.** `enable_backup_ref_ptr_instance_tracer` makes every `raw_ptr`/`raw_ref` construction call `InstanceTracer::TraceImpl` and every destruction call `UntraceImpl`; both take that one mutex, and `TraceImpl` inserts into a table (`GetStorage().try_emplace(...)`), which allocates. Chromium documents it as a test-end dangling-pointer aid and never ships with it on.
- **The holder** is the Compositor thread (thread 9), and it is deadlocked with itself:
  `cc::LayerTreeImpl::DiscardableImageMapUpdater::AddLayerNeedingUpdate` → (a `raw_ptr` is constructed) → `InstanceTracer::TraceImpl` **[takes the mutex]** → `try_emplace` → `operator new` → `base::allocator::dispatcher` → **GWP-ASan** sampled this allocation → `GuardedPageAllocator::Allocate` → `ReserveSlotAndMetadata` → `base::AutoLock(lock_)` was contended → `LockImpl::LockInternal` → `LockMetricsRecorder::ScopedLockAcquisitionTimer` (holds a `raw_ptr<LockMetricsRecorder>`) → after the SRW acquire succeeds the timer is destroyed → `raw_ptr` destructor → `InstanceTracer::UntraceImpl` → `std::mutex::lock` on the mutex **this same thread already holds** → blocked forever.
- **Everyone else** then queued on the tracer mutex through their own next `raw_ptr` construct/destruct: the main thread from `blink::scheduler::IdleTimeEstimator::DidProcessTask` → `cc::RollingTimeDeltaHistory::InsertSample` → `operator new` → GWP-ASan → `LockInternal` → timer → `TraceImpl` (it needed both the tracer mutex and, behind it, the GPA lock the Compositor holds); the IO thread from `MessagePumpForIO::GetIOItem`; the HangWatcher from `Histogram::Factory::Build` → `RangesManager::GetOrRegisterCanonicalRanges`; the ThreadPoolServiceThread from `ThreadControllerWithMessagePumpImpl::DoWorkImpl`; the new AudioOutputDevice thread from `~UncheckedScopedBlockingCall` in `media::AudioDeviceThread::ThreadMain`. Any thread that constructs or destroys a `raw_ptr` joins the queue, which in Chromium is every thread within seconds.
- **Why it needs several coincidences**, which is why months passed before the first hit: (1) a tracer insertion that allocates a new table node, (2) GWP-ASan choosing to sample exactly that allocation (renderer sampling multiplier 1500, range 12, i.e. roughly one in ten thousand allocations), (3) the guarded-page allocator's lock being contended at that instant by another thread (only the contended path constructs the metrics timer), (4) that timer's `raw_ptr` destructor being traced. Allocation-heavy moments (a busy agent pane, a compositor commit, a new audio thread) buy more tickets. Given enough runtime it is certain to recur on any binary built with the flag.
- **Where the flag came from.** `scripts/cef-build/args-windows.gn` line 57 had `enable_backup_ref_ptr_instance_tracer=true` since #2308 (2026-07-27), copied from a generated `args.gn`. Upstream CEF's `tools/gn_args.py` adds it for every non-debug **Windows** build (the outer condition is `is_debug or platform == 'windows' or is_asan`; macOS and Linux only get it in debug builds), so upstream's own Windows release binaries and the stock cef-dll-sys runtime `task dev` uses carry the same hazard. Our macOS and Linux args files do not set it. Every Windows runtime AgentMux has shipped since 148.0.7778.180 (2026-07-27) has been exposed.
- **Fix.** `enable_backup_ref_ptr_instance_tracer=false` in `scripts/cef-build/args-windows.gn` (done in this change set, with the rationale inline), rebuild the Windows CEF, publish a new `agentmuxai/cef` Windows release, bump `RELEASE_TAG` in `scripts/cef-build/fetch-patched-cef-windows.sh`. The rebuilt binary will also be measurably faster: the flag serialises every thread's `raw_ptr` traffic through one global mutex. Worth reporting upstream to CEF (their Windows release builds are affected) and to Chromium (the re-entrancy between `InstanceTracer` storage allocation, GWP-ASan and `LockMetricsRecorder` is a bug in the tracer even if Chrome never ships it).

## 4. What it was not

- Not AgentMux JavaScript: the block is inside base-library task bookkeeping below any page frame, and every other page in the same host was fine.
- Not srv, the launcher, the host process, the GPU process or the network service: all responsive, and srv's warning is downstream of the frontend not reading.
- Not the 2026-09-07 reactive-handler deadlock (#3084 is in this build) — that one wedged srv; this one wedged the renderer.
- Not a CEF upgrade in 0.56.12: the runtime is byte-identical to 0.56.10 and 0.56.11.
- Not memory pressure: renderer working set 264 MB, host 160 MB, 33 GB of RAM free.

## 5. Why now, and can it recur

Nothing changed in native code in 0.56.12; the flag has been in every Windows runtime since 2026-07-27. It is a probabilistic self-deadlock (§3a) whose per-allocation odds are tiny, so it took two months of daily use to land once. What was unusual at 22:42:05 was density: an agent in a 2–3 s tool loop (document updates, scroll-shrink attribution, a draggable-region recomputation every second, tool-tone sounds), a compositor commit, and a new audio output thread starting at that exact moment — more allocations per second, more lottery tickets. **It will recur on any binary built with the tracer on**, at random, and nothing in the product currently detects it. Until a rebuilt runtime ships, the right posture is to make it a ten-second blip instead of a dead window (§7).

## 6. Recovery procedure (validated 2026-09-23)

State lives in srv, so replacing the renderer loses nothing.

1. Confirm it is the renderer, not srv: `curl http://127.0.0.1:<srv-web-port>/` answers; `curl http://127.0.0.1:<host-devtools-port>/json/list` and a `Runtime.evaluate` against the main page times out. (`muxlog srv` showing `ws egress lane full` every second is the cheap tell.)
2. Optional, if evidence is wanted: `cdb -pv -p <renderer pid> -c ".dump /ma <path>; q"` (non-invasive; the process resumes).
3. `Stop-Process -Id <renderer pid> -Force` (PowerShell; `taskkill /PID` is mangled by Git Bash). Find the pid via the host's children with `--type=renderer` and the lowest `--renderer-client-id`, or via `SystemInfo.getProcessInfo` on the browser DevTools target.
4. The host's `on_render_process_terminated` path shows "AgentMux hit a problem — Reload window". Click Reload. The frontend reconnects to srv and every pane resumes.

## 7. Follow-ups

0. **Rebuild and ship the Windows CEF runtime with the tracer off** (§3a, args file already changed). This is the actual fix; everything below is defence in depth.
1. **Detect and auto-recover a hung renderer in the host.** The `cef` 152 binding already exposes `ImplRequestHandler::on_render_process_unresponsive(browser, callback)` / `on_render_process_responsive`; `agentmux-cef/src/client/handlers.rs` implements neither (only `on_before_browse` and `on_render_process_terminated`). Chromium fires it after its input-ack timeout once the user interacts with a hung page. Implementing it to log at `crash` level, wait one grace interval, then call `UnresponsiveProcessCallback::terminate()` routes straight into the recovery page that already exists — with an auto-Reload it becomes fully hands-off. This is the single highest-value change.
2. **Second detector that does not need user input.** srv already knows within 256 s that the frontend stopped reading (the egress lane). Turn N consecutive seconds of `egress lane full` on a connection into a `frontend_stalled` event to the host over the srv pipe, so the host can apply the same terminate-and-reload even when nobody clicks. The launcher's UI-liveness probe cannot see this case by design: it proves the browser UI thread pumped, and that thread was fine.
3. **Keep symbols for every `agentmuxai/cef` release.** The build already produces `libcef.dll.pdb` (5.4 GB); it is only discarded by omission. Two hours of this investigation went into proving upstream symbols cannot substitute, and the answer came in fifteen seconds once the local out-dir PDB was found. Minimum: compress the PDB (`7z -mx=5` or zstd; PDBs compress ~4–5×, under GitHub's 2 GB per-asset limit) and attach it to the same release tag as the runtime, plus the exact `args.gn` and the fork commit. Better: a symbol store (`symstore.exe add` into the existing S3 artifacts bucket, served over HTTPS so `_NT_SYMBOL_PATH` can point at it) — then any dump from any machine symbolises without hunting.
4. **Keep the dump.** `renderer-52384-frozen.dmp` should be moved somewhere durable before the scratch dir is cleaned; it is the reproduction artefact for the upstream reports in §3a.
4a. **Lint the GN args.** A short denylist check in `scripts/cef-build/configure-cef-build-windows.ps1` (and the macOS/Linux equivalents) that refuses to `gn gen` with any of `enable_backup_ref_ptr_instance_tracer`, `dcheck_always_on`, `is_debug`, `enable_backup_ref_ptr_slow_checks`, `is_asan` set to true, so a copied-from-generated-output args file cannot re-introduce a debug feature into a shipped runtime.
5. Low priority: the `on_draggable_regions_changed` callback firing every second at steady state (83 regions) is layout churn worth a look on its own, independent of this incident.
