## Spec coverage — what it proposes

The spec diagnoses 7 recurring symptoms (zombies, taskbar-without-window, pool-leak, instance-count inflation, tab-state divergence, InstancePanel flicker, burst tear-off pool exhaustion) as **one root cause**: state spread across **13+ stores in 4 processes** with no enforced invariants.

### Core architectural moves (§3)

- **Launcher = privileged owner** of all canonical state (windows, processes, warm pool, lifecycle phase). Holds the Job Object. Currently the launcher is just a thin spawner — the spec inverts this so the launcher outlives any host crash.
- **Host = stateless executor.** Owns CEF/HWNDs but reports state up, takes commands down.
- **Frontend = passive mirror** of an event stream from the launcher. No more polling.
- **Warm pool = separate type**, mirrors Chromium's `SpareRenderProcessHostManager`. Pool items NEVER appear in the main registry until promotion. **Single invariant kills the entire "pool window leaks to taskbar / inflates count" bug class by construction.**

### 6-state window FSM (§4.1)

```
              spawnFailed
           ┌────────────────┐
           │                ▼
Requested ─►  Spawning  ─► (terminal)
              │
              ▼
          ReadyHidden ──promote──► Visible ──userClose──► Closing ──► Closed
              │                       │                                ▲
              │                       │   crash                        │
              │                       └───────────────────────────────►│
              │ idleEvict                                              │
              ▼                                                        │
           Closed ◄────────────────────────────────────────────────────┘
```

All transitions named, observable, exhaustively matched. No "crashed but tracked" state — destroyed signal is the only authoritative one (lesson from Chromium's `WebContentsObserver::WebContentsDestroyed`).

### Process model (§4.3)

Per-`ProcessRecord` tracking with kind (`Host | Srv | Renderer { parent_window: WindowId }`), state, job assignment status. Single Job Object on launcher; CEF render children inherit it. Every child launched with `CREATE_SUSPENDED`, assigned to job, then `ResumeThread` — the standard Windows pattern documented by Microsoft and Raymond Chen, and what Chrome itself uses.

### 6 enforced invariants (§7)

Checked at transition boundaries. Violations panic the launcher (which the OS recovers via Job-Object cleanup — explicitly preferred over silent corruption).

## Concrete fix for the race condition

Use `std::os::windows::process::CommandExt::creation_flags(CREATE_SUSPENDED)` so the host process is created in a suspended state. Then `AssignProcessToJobObject` is guaranteed to land before any code in the host runs. After assignment, find the host's main thread via `Toolhelp32` snapshot and `ResumeThread`.

Sketch:

```rust
use std::os::windows::process::CommandExt;
use windows_sys::Win32::System::Threading::CREATE_SUSPENDED;

let mut child = std::process::Command::new(&real_exe)
    .args(&args)
    .creation_flags(CREATE_SUSPENDED)
    .spawn()?;
let host_pid = child.id();

// Job assignment runs while host is frozen — no children can spawn yet.
let job = create_job_object_for_child(host_pid)?;

// Find the host's only thread (main, since CREATE_SUSPENDED) and resume.
resume_main_thread(host_pid)?;

// Existing wait path follows.
child.wait()?;
```

`resume_main_thread` enumerates `Toolhelp32` thread snapshot, finds the `THREADENTRY32` whose `th32OwnerProcessID == pid`, and `ResumeThread`s it via `OpenThread(THREAD_SUSPEND_RESUME, ...)`. With `CREATE_SUSPENDED` only the main thread exists, so the search returns exactly one entry.

All windows-sys APIs needed are already in scope:

- `windows_sys::Win32::System::Threading::CREATE_SUSPENDED`
- `windows_sys::Win32::System::Threading::OpenThread`
- `windows_sys::Win32::System::Threading::ResumeThread`
- `windows_sys::Win32::System::Threading::THREAD_SUSPEND_RESUME`
- `windows_sys::Win32::System::Diagnostics::ToolHelp::CreateToolhelp32Snapshot`
- `windows_sys::Win32::System::Diagnostics::ToolHelp::Thread32First`
- `windows_sys::Win32::System::Diagnostics::ToolHelp::Thread32Next`
- `windows_sys::Win32::System::Diagnostics::ToolHelp::TH32CS_SNAPTHREAD`
- `windows_sys::Win32::System::Diagnostics::ToolHelp::THREADENTRY32`

May need an additional `Win32_System_Diagnostics_ToolHelp` feature in `agentmux-launcher/Cargo.toml`.
