# Retro: agent pane still shows a raw random slug tag (e.g. `hazy-mapping-alpaca`) via the legacy standalone Subagent pane

**Date:** 2026-07-28
**Severity:** P2 — cosmetic/trust issue (a live user-facing surface the team believed was retired), not data loss or a crash
**Status:** Root-caused and **fully removed** (updated 2026-07-28, same day). Initial diagnosis proposed re-homing the in-transcript click into the Swarm pane (§6 Option B below); the user's explicit follow-up direction was narrower and stronger — no replacement pane, no replacement inline indicator, full removal of the click-to-open scaffold and the raw-slug-bearing inline chip. See §9 for what actually shipped.

---

## 1. What the user reported

> In the running AgentMux instance, why do we still see the agent coming in
> as "hazy-mapping-alpaca" as these sort of tags inside the agent pane? we
> were supposed to remove it, in fact, the panel it generates off of should
> not even exist. write a retro on how it was introduced and how it can be
> completely removed. there is never a time we should get it.

## 2. Where the tag actually comes from — it isn't generated by AgentMux at all

The three-word hyphenated string (`hazy-mapping-alpaca`, or the real example
already documented elsewhere as `quizzical-tumbling-valiant`) is **not**
produced by any word-list/petname generator inside this codebase. There is no
such generator anywhere in `agentmux-srv` or `frontend/app` — confirmed by
grepping both trees and `Cargo.toml`/`Cargo.lock`/`package.json` for
`petname`, `random-word`, `unique-names-generator`, `docker-names`, and
similar, with zero hits.

It is the **Claude Code CLI's own per-session `slug`**, read verbatim off the
first line of a subagent's JSONL transcript:

> "Raw display names are ugly by design, not by bug: `slug` comes from the
> subagent's own JSONL first line's `"slug"` field
> (`subagent_watcher.rs:1004-1012`); if the CLI didn't write one, it falls
> back to the raw `agentId` hash (`:1013-1027`)."
> — `docs/specs/REPORT_SWARM_SUBAGENT_DETAIL_UX_ANALYSIS_2026_07_07.md:45-48`

AgentMux reads this field (`agentmux-srv/src/backend/subagent_watcher/parse.rs`)
but does not invent it. So "remove the generator" is not an available fix —
the fix has to be "never surface this raw external field as a name," which
the rest of the naming system (below) already does correctly in one place and
not in another.

## 3. There are two independent ways to view a subagent's detail — only one was ever fixed

**Swarm pane row** (`frontend/app/view/swarm/`) — **fixed**, 2026-07-07
onward. Clicking a Swarm-pane row expands inline and shows the Haiku-resolved
`display_name` (`subagent.GenerateName` RPC,
`agentmux-srv/src/server/app_api/session.rs`), falling back to the raw slug
only transiently while naming is in flight.

**The legacy standalone `SubagentView` split-pane — never fixed, still shows
the raw slug unconditionally:**

- `frontend/app/view/subagent/subagent-model.ts:81-86`:
  ```ts
  this.viewName = () => {
      const info = this.infoAtom();
      if (info?.slug) return info.slug;
      if (this.subagentId) return this.subagentId.substring(0, 7);
      return "Subagent";
  };
  ```
  This is the tab title. It never calls `subagent.GenerateName` and never
  reads `display_name` — those fields don't even exist on this file's
  `SubagentInfo` interface (compare to the Swarm pane's `WorkflowDispatch`
  types, which do carry `display_name`).
- `frontend/app/view/subagent/subagent-view.tsx:94-95` — the in-pane header
  is the same raw value: `info()!.slug || info()!.agent_id`.
- **Trigger**: this pane opens when a user clicks a subagent link rendered
  *inline in an agent's own transcript* (e.g. a `Task` tool-call line),
  handled by `SubagentLinkBlock.tsx` → `agent-view.tsx:1348`
  (`handleSubagentClick`) → `frontend/app/store/subagent-pane-manager.ts:28`
  (`openSubagentPane`), which splits a brand-new block with
  `meta.view = "subagent"` next to the parent agent pane. This is a
  **completely separate code path** from the Swarm pane — clicking a link in
  a transcript never goes anywhere near `swarm-model.ts`.
- The view is still fully registered and reachable:
  `frontend/app/block/block-registry.ts:34` —
  `blockViewRegistry.set("subagent", SubagentViewModel as any)` — and
  `blockutil.tsx:21` gives it the label `"Subagent"`.

This exactly matches the report: a real, still-openable pane, titled with
Claude Code's raw session slug, sitting entirely outside the naming fix that
shipped for the Swarm pane.

## 4. "We were supposed to remove it" — true, twice, and both times the team explicitly chose not to

This is not a case of nobody noticing. It was raised and consciously deferred
**twice**:

**2026-07-07** — `docs/specs/REPORT_SWARM_SUBAGENT_DETAIL_UX_ANALYSIS_2026_07_07.md`,
"Resolution of the open questions," §1:

> "**Standalone `SubagentView` pane: kept, not retired.** Discovered during
> implementation that `agent-view.tsx`'s `handleSubagentClick` (a subagent
> link rendered inline in an agent's own transcript, e.g. a Task-tool
> invocation) also calls `openSubagentPane` — a second, independent entry
> point beyond the Swarm tree that `CLAUDE.md`'s 'Not widgets' table didn't
> account for. Retiring the pane would have broken that click-through, so
> `subagent-view.tsx` / `subagent-model.ts` / `subagent-pane-manager.ts`
> [are untouched]."

This same document, ten lines earlier in its analysis section, had explicitly
*recommended* retiring these files as dead code once the Swarm pane grew
inline expand — the "kept, not retired" line is a deliberate reversal made
mid-implementation, not an oversight.

**2026-07-17** — `docs/specs/SPEC_AGENT_DISPATCH_SUBAGENT_HIERARCHY_2026_07_17.md`,
§6, raised it again and again declined to resolve it:

> "`frontend/app/view/subagent/subagent-model.ts` (the older, non-workflow-
> aware standalone pane) is a decision point this spec surfaces but doesn't
> resolve: retire it in favor of the Swarm pane exclusively, or bring it onto
> the new two-level model too. Flagging rather than deciding since it's a
> product-surface call, not a schema one."

The follow-up work that actually shipped from that spec chain
(`docs/specs/SPEC_SWARM_DISPATCH_NAMING_AND_ROW_MODEL_2026_07_19.md`, landed
via PR #2231 / #2232 — eager per-dispatch Haiku naming + the two-bucket
Agent-Tool/Workflow row model) only touched Swarm-pane code
(`swarm-model.ts`, `swarm-view.tsx`, `swarm-model.test.ts`). It never
revisited the standalone pane or its second entry point. **Nobody ever came
back to make the "retire it" call** — the two decision points each correctly
identified the blocker (the transcript click-through has nowhere else to go)
and each time the follow-up task ("then go build it a new home and delete
this") silently dropped off the plan.

**A likely reason the team believes this was already handled**:
`CLAUDE.md`'s own "Not widgets" table (root `CLAUDE.md`, "Subagent" row)
currently reads:

> "Spawned by clicking a sub-agent in the Swarm pane's overview. Not a
> top-level pane type the user opens directly."

This is **stale and actively misleading** as of 2026-07-07: the Swarm pane
hasn't opened this standalone pane since that date's inline-expand change —
only the in-transcript link click still does, and it does open it directly,
as its own top-level split pane. Anyone reading `CLAUDE.md` today would
reasonably conclude the split-pane path had been fully replaced by the Swarm
pane's inline expand, which is exactly the "we were supposed to remove it"
belief in the bug report. This doc line is the most likely single source of
that belief and should be corrected regardless of which fix option is taken
(§6).

`git log --follow` on both `subagent-model.ts` and `subagent-pane-manager.ts`
shows only additive history ending at the commits above — **no commit ever
attempted to remove these files.** The "removal" that the user remembers is
almost certainly the Swarm-pane naming fix (§3) plus the stale `CLAUDE.md`
line (§4) creating the impression that the whole feature had been retired,
when in fact only one of its two entry points was ever touched.

## 6. How to completely remove it

Two options exist; only one matches "there is never a time we should get
it."

### Option A — naming parity only (rejected; doesn't satisfy the ask)

Wire `SubagentViewModel` (`subagent-model.ts`) to `display_name` /
`subagent.GenerateName`, mirroring what `swarm-model.ts` already does. This
would stop the raw-slug tag from appearing, but the standalone pane itself —
the thing the user explicitly said "should not even exist" — would still be
there. Documenting this option for completeness only; **not recommended.**

### Option B — actually retire the pane (matches the ask)

1. **Give the in-transcript click-through a home that isn't a new split
   pane.** `handleSubagentClick` (`agent-view.tsx:1348`) currently has no
   substitute — the Swarm pane has no existing "focus subagent X inline,
   triggered from outside the Swarm tree" API today (`swarm-model.ts`'s
   exports are all internal row-building/merging helpers, not a
   jump-to-dispatch entry point). This is real, scoped work, not a pure
   deletion: either (i) add a "reveal this subagent in the Swarm pane"
   action — open/focus the Swarm pane and scroll+expand the matching row (a
   `subagentId` → dispatch-row lookup already exists implicitly via
   `swarm-model.ts`'s `subagentRowKey`/`groupCacheKey` machinery, so this is
   additive, not a new data model), or (ii) render the transcript link as a
   Swarm-pane deep link/inline summary instead of a clickable pane-opener.
2. **Once (1) ships and the transcript click no longer calls
   `openSubagentPane`, delete:**
   - `frontend/app/view/subagent/subagent-view.tsx`
   - `frontend/app/view/subagent/subagent-model.ts`
   - `frontend/app/view/subagent/subagent.ts`
   - `frontend/app/view/subagent/subagent-view.scss`
   - `frontend/app/store/subagent-pane-manager.ts`
   - the `"subagent"` view registration:
     `frontend/app/block/block-registry.ts:34` and the `VIEW_LABELS["subagent"]`
     entry in `frontend/app/block/blockutil.tsx:21`
   - `handleSubagentClick`'s now-dead imports (`isSubagentPaneOpen`,
     `openSubagentPane`) in `agent-view.tsx`
3. **Correct `CLAUDE.md`'s "Not widgets" table** — either delete the
   "Subagent" row entirely (if step 1/2 removes the concept of a standalone
   subagent pane) or rewrite it to describe the real, new entry point
   accurately. Leaving it as-is, even after the code changes, would
   reproduce the exact misunderstanding that led to this report.
4. **Add a regression test** asserting `"subagent"` is not a registered
   block view type (or equivalent), so a future re-introduction of a
   standalone subagent pane is caught at review time rather than requiring
   another live-instance bug report to notice.

## 7. What's confirmed vs. what's a design call

**Confirmed (read directly from source and git history, not inferred):**
- The tag is Claude Code's own JSONL `slug` field, not an AgentMux-generated
  random name.
- `subagent-model.ts:81-86` and `subagent-view.tsx:94-95` render that raw
  field unconditionally, with no `display_name`/`GenerateName` path.
- The in-transcript click (`agent-view.tsx:1348` → `subagent-pane-manager.ts:28`)
  is a live, independent trigger, distinct from the Swarm pane, and is still
  fully wired and registered (`block-registry.ts:34`).
- Two prior specs (2026-07-07, 2026-07-17) explicitly considered retiring
  this pane and both times deliberately kept it, citing the same
  click-through blocker, without ever resolving the blocker afterward.
- No commit in this file's history ever removed or attempted to remove it.
- `CLAUDE.md`'s current description of this surface is stale as of
  2026-07-07 and is the most likely source of the belief it was already gone.

**Design call, not yet decided (this retro does not decide it):**
- Exactly how the in-transcript click should be re-homed (reveal-in-Swarm-pane
  vs. inline summary vs. something else) — flagged as a "product-surface
  call" by the 2026-07-17 spec, and still is one. Whoever picks this up
  should make that call explicitly rather than deferring it a third time.

## 8. What actually shipped (2026-07-28, same day)

The user's follow-up was explicit: no split pane at all, and no raw slug
anywhere in the agent pane — "if claude needs them, keep them out of the
agent pane." Investigating the inline chip's own renderer
(`SubagentLinkBlock.tsx`) surfaced that IT, not just the split pane's tab
title, was the actual "tag inside the agent pane" the report described — it
rendered `props.node.slug` directly as visible text
(`agent-subagent-link-slug`), independent of whether the pane it opened had
ever been clicked. Investigating further also surfaced a **third**,
previously-unlisted entry point: `ToolBlock.tsx`'s "⧉ Open subagent in new
pane" button on any `tool === "Agent"` row, which called `createBlock({meta:
{view: "subagent", ...}})` directly — bypassing `subagent-pane-manager.ts`
entirely, so it wasn't caught by grepping for `openSubagentPane`.

**All three entry points, the split pane, and the inline chip were removed
outright — no replacement pane, no replacement inline indicator.** Subagent
activity remains visible only in the Swarm pane (and the ActivityDock, an
independent third consumer of the same `subagent:spawned`/`subagent:completed`
broadcast via `activity/subagent-source.ts`, unaffected by this change).

Deleted:
- `frontend/app/view/subagent/{subagent-view.tsx,subagent-model.ts,subagent.ts,subagent-view.scss}`
- `frontend/app/store/subagent-pane-manager.ts`
- `frontend/app/view/agent/components/SubagentLinkBlock.tsx`
- `frontend/app/view/agent/hooks/useSubagentEvents.ts`

Edited (removed all references to the above, end to end):
- `frontend/app/block/block-registry.ts`, `blockutil.tsx` — `"subagent"` view registration + icon/label
- `frontend/app/view/agent/agent-view.tsx` — `handleSubagentClick`, `useSubagentEvents` call, `onSubagentClick` prop
- `frontend/app/view/agent/components/{AgentDocumentView,ToolBlock}.tsx` — prop threading; the "⧉" button entirely
- `frontend/app/view/agent/virtualization/{AgentDocumentVirtualList,DocumentRow,renderers,expansion-source,index}.ts(x)` — `subagent_link` `DocumentNode` variant removed from the estimator/streaming-capability/expansion registries end to end
- `frontend/app/view/agent/types.ts` — `SubagentLinkNode` interface and its `DocumentNode` union member deleted
- `frontend/app/view/agent/hooks/useInSessionSearch.ts` — search-text case
- `frontend/app/view/agent/styles/_document-nodes.scss` — `.agent-subagent-link` and `.agent-tool-open-pane` style blocks
- Test files (`renderers.test.ts`, `expansion-source.test.ts`, `perf-probe.test.ts`) updated to drop subagent-link-specific fixtures/assertions
- `CLAUDE.md`'s stale "Subagent" row in the "Not widgets" table — deleted (the surface it described no longer exists)

Verified clean: `tsc --noEmit` (0 errors) and the full frontend `vitest` suite
(2008 passed, 3 skipped, 0 failed — one `tool-renderers/registry.test.ts`
timeout in the first full-suite run was confirmed unrelated and non-reproducing
in isolation, a pre-existing parallel-run flake, not a regression from this
change).
