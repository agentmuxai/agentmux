# RCA: issues seen after an in-app upgrade from 0.59.30 to 0.59.34 (2026-10-19)

**Status:** analysis

One upgrade on Windows, a local build channel, showed several problems at once. Each section says what was seen, the root cause in the code and the fix. Every version keeps its own data directory (`versions/<version>/data`), and the new srv carries the previous version's data forward at its first start.

## 4. "Show folder" does nothing

**Seen.** In the version panel, once an update had downloaded, "Show folder" did nothing. The click came from the old version's window, before the restart. In the new version the button appears only once another update downloads, because the download's state lives only in the old srv's memory. The host's debug log has `Error: Unknown command: open_native_path` for each click. The host log shows only `ERROR [fe] {}`, because the Error object serialises to `{}`. The target folder existed.

**Root cause.**
- `frontend/app/statusbar/MaintenanceSection.tsx:325` calls `getApi().openNativePath(folder)`.
- `frontend/util/cef-api.ts:194-196` sends the IPC command `open_native_path` and ends with `.catch(console.error)`, without awaiting it.
- The CEF host's router (`crates/cef/src/ipc.rs`, `route_command`) has no such command, and never has (`git log -S'"open_native_path"' -- crates` is empty; it dates from the Tauri host). The request falls to `Unknown command` (`ipc.rs:1192`). The routed sibling is `reveal_in_file_explorer` (`ipc.rs:333`, in `crates/cef/src/commands/platform.rs:959-1013`).
- The button came with #5000. Its test (`frontend/app/statusbar/UpdateStatus.test.tsx:148-153`) mocks `openNativePath` and checks only that it was called, so nothing checks that the host routes the command.
- `docs/analysis/ANALYSIS_READ_TOOL_PREVIEW_2026_10_01.md:140` already noted that `openNativePath` falls through to "Unknown command".

**Same bug elsewhere.** The widgets settings' "Show folder" (`frontend/app/view/settings/sections/widgets-section.tsx:176` and `:275`, from #4575).

**Fix.**
1. Call `revealInFileExplorer(folder)` in all three places, and update the test.
2. Remove `openNativePath` from `cef-api.ts` and `custom.d.ts`. Don't add a host command that opens an arbitrary path through the shell: for an executable that would run it.
3. Await the call and show an error, as the other Maintenance actions do. The `[fe]` log forwarder sends `Error: <message>` rather than `{}`.
4. Add a test that every command `cef-api.ts` sends has a route in `crates/cef/src/ipc.rs` (`cef-api.routes.test.ts`).

Done in #5195.

## 7. The new version runs from inside the old version's data folder

**Seen.** srv couldn't move the unpacked update into place beside the running portable ("Access is denied", os error 5). It fell back to `versions/0.59.30/data/updates/0.59.34/`, and 0.59.34 runs from there.

**Root cause.**
- **The unpack worked; the move didn't.** `unpack_portable` (`crates/srv/src/backend/update_download.rs`) unpacks into a `.partial` folder and then renames it into place. On Windows a folder can't be renamed while a file inside is open without delete sharing, and a folder of just-written executables is routinely still open to the antivirus scanner. The rename was tried once. The parent folder was otherwise writable: earlier portables were unpacked there.
- **The fallback was the old version's data folder:** `updates_root()/<version>`, which is this version's `data/updates/`. So:
  - removing an old version's data, by hand or by a future cleanup, would delete the running build;
  - every later update whose move fails nests one level deeper.

  No code removes old version folders today.

**Fix** (in this PR):
- **Retry the move:** `rename_when_free` tries the rename again on "Access is denied" for up to 10 seconds, waiting 0.25 s, then 0.5 s, 1 s and 2 s.
- **Move the fallback:** `fallback_parent` puts the unpacked portable, or a Linux AppImage, in `<channel>/updates/<version>/`, outside every version's data folder.
- **Launcher:** on Windows it accepts a staged portable in any folder. On Linux, `upgrade_linux::check_target` now also accepts the channel's `updates/<version>/` (`staged()` takes the channel dir).
- **Tests:**
  - the fallback's location;
  - a rename that works is immediate;
  - a missing source fails at once;
  - on Windows, a rename refused while a file inside is open goes through once it closes;
  - on Linux, the launcher accepts the channel folder and refuses another channel's.
- **Not removed automatically:** what is unpacked there may be the version the user runs, like a portable beside the running one.

- **No staging beside a build in the channel's tree:** when the running build is anywhere under the channel's folder (`beside_parent`), the next version goes straight to `<channel>/updates/<version>/`. That covers a build itself put in a fallback, whether the channel's own or an old version's `data/updates/`. Staging beside it would nest the new version under the old one's folder.

**An instance already affected** runs from inside the old data folder until its next update, which now moves it out to the channel's `updates/`. Don't remove the old folder before then.

## 8. A No to the restart question leaves the panel stuck on "Restarting"

**Seen.** Upgrade & restart, then No in the confirmation dialog: the version panel kept showing "Restarting: answer the AgentMux dialog (No cancels)", with no Upgrade button, so the upgrade couldn't be tried again.

**Root cause.**
- srv starts the restart by printing a line the launcher reads (`AGENTMUXSRV-UPGRADE`), sets the download's state to `restarting`, and then sleeps `RESTART_GRACE` (3 minutes, `crates/srv/src/backend/update_restart.rs`) before it believes the restart didn't happen.
- The launcher asks the question (`ask_then`, `crates/launcher/src/upgrade_restart.rs`) and, on No, simply returns. Nothing tells srv. Cancel in the panel is refused in this state, because only the dialog can say no (`cancel()`).
- So a No leaves the panel in `restarting` until the grace runs out, up to three minutes. A question that lapses unanswered (150 s) does the same.

**Fix.** On a No, or when the question lapses, the launcher leaves `updates/declined.txt` in the data folder (the same folder srv already uses to pass it `stopping.txt`), only for the newest request so a newer question's closing of an older dialog doesn't count. srv clears the file before it asks, then checks for it every two seconds while it waits; a file naming the version it asked about is taken out as it is read, and the panel goes back to `ready` at once, without an error. Clearing and taking it out (rather than comparing times) means an answer from an earlier attempt can't answer a new question, however soon the user tries again. Tests: srv takes a No once and only for the version asked; the launcher writes the file under the name srv reads.

## 5. The layout looked lost

**Seen.** At the new version's first start, srv logged that carry-forward started from the previous version's data, then `[srv-persist] bootstrap loaded 0 workspace(s) + 0 tab(s) + 0 block(s) + 0 window(s) from mstore`. The agent pane came back with a new block id.

**What actually happened: the layout was carried and restored.**
- **Carry-forward** (`crates/srv/src/bootstrap/carry_forward.rs`, #4996) copies `filestore.db`, `sagas.db` and `objects.db` from the previous version with `VACUUM INTO` on a read-only connection (`:52-72`). That includes committed WAL content. It ran after the old srv had stopped.
- **A quit deletes the workspace, tab, block and window rows on purpose.** The layout is kept in `Client.meta["session:last_topology"]` (`session_restore.rs:42`), written by `snapshot_session` at the quit.
- **So "loaded 0" is expected after every quit.**
- **The first window's `CreateWindow` rebuilt the layout from the record** (`window_create.rs:44-79` → `restore_last_session`, `session_restore.rs:552`). Checked on copies of both databases:
  - the restored layout matches the saved one, node for node, including a minimized pane;
  - the client meta is empty afterwards, which happens only after a successful restore.
- **New block ids are by design:** `CreateBlock` always mints new ids (`session_restore.rs:52-56`). The agent resumed the same provider session.

**Gaps.**
- **No log line on restore.** A one-window restore logs nothing, so "loaded 0" reads like data loss. Add "session_restore: restored N window(s) from the quit record".
- **Position and size are not restored:** the main window opens where the host puts it. This is already listed under "Not yet" in `SPEC_UPGRADE_FOR_USERS_AND_AGENTS_2026_10_15.md` §6.1.

## 2 and 3. Theme, opacity and window title lost

**Seen.** The window had a custom name, a non-default theme and opacity. After the upgrade it had no name and the default theme.

**Root cause, title.** A quit record is written by the version that quits. Saving window names in the record (`session_windows.rs:119-121`) and applying them on restore (`window_create.rs`) came with #5101, first released in 0.59.33. 0.59.30's `snapshot_session` saved position and size only, so 0.59.34 had no name to apply. From 0.59.33 on, the name survives.

**Root cause, theme and opacity.**
- Since #4798 (0.59.23) they live only in `Window.meta["window:theme"]` and `["window:opacity"]` (`frontend/app/store/window-appearance.ts:24-29, 70-74`).
- A quit deletes the Window row, and `snapshot_session` (`session_windows.rs:106-137`) saves only x, y, width, height and the name. This is still true in 0.59.35.
- `SPEC_PER_WINDOW_THEME_AND_OPACITY_2026_10_12.md` (§1) assumes session restore keeps each window's saved meta from its Window rows. That stopped being true when a graceful quit began deleting those rows (`SPEC_SESSION_RESTORE_AND_SAVED_LAYOUTS_2026_08_13.md`).
- So theme and opacity are lost on **every** quit and relaunch, not only on upgrades. This comes from reading the code and hasn't been reproduced yet.

**Fix.**
- **Save:** `snapshot_session` also saves each window's per-window appearance keys, `window:theme` and `window:opacity`, at a quit and at the last window's close.
  - `window:transparent` is not among them: it is an app-wide setting in `settings.json`, read before any window exists, not Window meta.
- **Restore:** generalise `session:restored_window_names` to the window's meta, and have `CreateWindow` write it onto the new Window row next to the name. Log `session_restore: restored N window(s) from the quit record` (or "last-close" for a close's record).
- **Spec:** correct the per-window theme spec's claim.
- **Test:** quit and restore, then check that the name, theme and opacity come back.
- **When it helps:** only for quits made by a version that has the fix, since the quitting version writes the record.

In #5200.

## 6. The shared transcript store is corrupt for some agents' transcripts

**Seen.**
- **Where:** every instance on a machine writes agent transcripts to one shared SQLite store, `~/.agentmux/shared/agents/transcripts/filestore.db`.
- **What fails:** appends to a few agents' transcripts fail with `sqlite error: database disk image is malformed`, logged as `global transcripts: append failed`. Reads of those transcripts' tails fail the same way. Other agents' transcripts keep working.
- **When:** it started on one day in two srv processes of different versions within a minute of each other, then reached more agents on later days.
- **Not hardware:** no srv crash, no OS crash, and no disk, NTFS or hardware (WHEA) errors were logged.
- **Effect:** a pane that opens an affected agent has no history to show beyond the live session.
- **Was silent:** the failure was only a WARN line in srv's log. Since #5204 the first corrupt error on a zone is an incident and isolates that zone for the process (see "Silent by design today" below); nothing repairs the damage.

**How the store works** (`crates/srv/src/backend/storage/filestore/`, opened in `bootstrap/stores.rs:370-393`).
- **Settings:** WAL mode, `synchronous=NORMAL`, `busy_timeout=5000`; the writer turns automatic checkpoints off (`core.rs:147-150, 220-262`).
- **Connections:** each srv process has one writer, a reader pool (from 0.59.12) and a background checkpoint thread with its own connection. Every srv on the machine (several run at once) opens the same file.
- **SQLite:** every build bundles 3.45.0 (`libsqlite3-sys 0.28.0`).
- **Layout:** a file is a row in `db_file_data` per 64 KB part, keyed by (zone, name, part index). An append reads the zone's file row and last part, then rewrites them in one transaction.
- **Why only some agents fail:** "malformed" comes only from a query that walks a damaged page. Each zone's appends touch the same few pages, so a zone whose last part, overflow chain or index leaf is damaged fails on every append, while other zones never reach those pages.

**Root cause (most likely): SQLite's WAL-reset corruption bug, which this checkpointing design makes frequent.**
- **The bug** (sqlite.org `wal.html` §11; release log 3.51.3): it affects databases in WAL mode "when there are two or more database connections open on the same file, in separate threads or processes, and when those two connections attempt to write or checkpoint at the same instant".
  - A checkpoint that misses a WAL reset leaves the WAL index claiming frames are already copied, and a later checkpoint skips part of a transaction.
  - It is present from 3.7.0 to 3.51.2 and fixed in 3.51.3. Backports exist for 3.44.6 and 3.50.7, none for 3.45.
- **Why this app hits it often:** each srv's checkpoint thread runs `PRAGMA wal_checkpoint(PASSIVE)` whenever the WAL *file* is at least 4 MB, checking every 250 ms (`checkpointer.rs:27-29, 53-55`).
  - A WAL file doesn't shrink unless it is truncated, and the shared store never is: the periodic `wal_checkpoint(TRUNCATE)` covers only the per-channel store (`main.rs:270`, `shutdown.rs:86-110`), and no `journal_size_limit` is set.
  - So once the shared WAL has passed 4 MB, every srv checkpoints it about four times a second, indefinitely, while every srv's writer keeps committing. Heavy machine load widens the timing windows.
- **It fits what was seen:**
  - no crash and no hardware errors;
  - the damage is in the pages being written at that moment (the active transcripts' tails);
  - two processes saw it within a minute;
  - more agents were affected on later days, so it keeps happening rather than coming from one event.
- **Not yet confirmed:** this is a match by version and pattern; the failure hasn't been reproduced, and the damaged file hasn't been examined. To confirm, run `PRAGMA integrity_check` on a copy taken with every instance stopped. This bug typically shows as "row N missing from index" or wrong index entry counts.

**Ruled out or unlikely:**
- **Raw file handling:** no code copies, truncates or vacuums the shared store. `carry_forward.rs` and `snapshot.rs` touch only per-channel stores.
- **Schema differences between versions:** none (`FILESTORE_SCHEMA_VERSION=1` throughout; the same column and trigger setup since #3631).
- **`synchronous=NORMAL`:** in WAL mode it can't corrupt on an app crash, and there was no OS crash.
- **Storage-layer changes in the week before:** none that could damage pages.
- **Not checked:** an outside tool (a `sqlite3` CLI, antivirus, backup or sync) writing to the file.

**Risk.** The damage is probably confined to those transcripts' pages for now, but the whole file is at risk. A damaged free-page list or btree can make SQLite reuse a page that is still in use and overwrite healthy data. Nothing stops writes, and the bug is live in every build until the upgrade.

**Silent by design (before #5204).** Appends to the shared store, tail reads and index rebuilds only logged a WARN, and no code treated SQLITE_CORRUPT specially, checked integrity, told the user or isolated the damage.

**Since #5204.** The first `ErrorCode::DatabaseCorrupt` on an agent's zone, from an append, a tail read or an index rebuild or read, marks the zone damaged for the rest of that process (`backend/transcript/damage.rs`):
- appends to it skip the shared store, and the block's own copy keeps being written, with or without `agent:transcriptsinglecopy`;
- the pane's read path and the My Agents preview use the block's own copy;
- one `transcript_damaged` incident per agent id (the id in the zone's name: the transcript's and the segment log's are the same string when the code's own comments hold, which is not checked) is written to `incidents.jsonl` and shown in every open window at once (the `incident:recorded` event), and the agent gets one `[AgentMux]` system note.
- the resume check and packet tail, the agent's segment log, the running summary (continuity state), archives and the snapshot mirror do the same for their reads and writes of the zone (#5204 follow-up): they skip it and use the channel's own copy where there is one.
- an agent's memory record (writes, captures, the bundle sidecar, the reconcile before a spawn) and Global Memory's record are marked the same way under their own keys, with their own words in the notice and no note to the agent; they have no copy of their own, so they are left alone, not read from elsewhere (#5204 follow-up).
- the Agent History list, its size indicator and the agent record (history search) leave a zone found corrupt out, with the rest still listed, instead of one corrupt zone failing the list for every agent (#5204 follow-up).
- **Not yet:** fork history of the shared store still only logs a WARN; the mark is per process; nothing repairs the file or runs a periodic `quick_check`.

**What is lost and what can be recovered.**
- **Lost from the shared store:** every line whose append failed, plus whatever sat on the damaged pages.
- **The per-channel copy:** each instance also writes the block's `output` to its own `versions/<v>/data/db/filestore.db`, before the shared mirror (`file_ops.rs:170-225`, then `241-245`). Older version folders keep their own copies, and `transcript_backfill.rs` can already rebuild a shared zone from the richest per-channel copy. This is the main recovery source.
- **The provider's own session files** (for Claude, JSONL under the identity's `projects` folder): the full conversation, in a format the pane can't render. Resume uses them, so the agents' own context is intact.
- **The WAL:** it may hold newer page images. Keep it with the db; never delete it.

**Recovery (every instance on the machine must be stopped).**
1. Quit every AgentMux instance. A file copy taken while they run is inconsistent.
2. Copy `filestore.db`, `-wal` and `-shm` together to a disk with room for two copies. Leave the originals untouched.
3. On the copy, with a sqlite3 CLI at 3.51.3 or later, run `PRAGMA integrity_check(1000);` and record what is damaged.
4. Recover into a new file: `sqlite3 copy.db ".recover" | sqlite3 recovered.db`, then check the result's integrity.
5. List the zones whose parts have gaps: for each (zone, name), the parts must run from 0 to the last without gaps.
6. For those zones, drop the `output`, `output.tsidx` and `output.idx` rows, and rebuild them from the per-channel copies (the `transcript_backfill` logic).
7. With everything still stopped, move the old files aside, put the recovered file in place with no `-wal` or `-shm`, and start one instance first.

**The repair (2026-10-22).** Run with the recovery tool (#5206) after every instance on the machine was stopped:
- **What it found:** 5 damaged files in 3 transcripts, out of 1,169 files in 399 transcripts. `.recover` restored everything else, including the page-level damage the earlier errors pointed at.
- **What it did:** the rebuilt store passed its integrity check, kept the shared store's schema version, and was put in place. The original files were renamed beside it, not deleted. Two damaged search sidecars (`output.tsidx`) were dropped for the app to rebuild.
- **What it left:** three transcripts with no complete copy to rebuild from. Two lost their last block (tens of KB at the end of about 1 GB each), and one has a block of zeros mid-file.
- **Not the cause, but confirmed:** a build older than 0.59.36 refuses the repaired store, as designed (#5203), and shows its agents with almost no history because it falls back to its own per-channel copy. Run 0.59.36 or later.

**A transcript missing its last block opened a blank pane.**
- **What happened:** an agent pane opens at the newest lines. For a transcript whose last block was lost, that read hit the gap. srv treats a part missing inside a file's size as "not stored yet", because a build without transactions raises the size before it stores the parts. The pane recorded the failure (`InitFailed`) but nothing showed it, so the agent looked as if it had no history. Reopening the pane after new output had overwritten the block worked.
- **Fix:**
  - **srv** (`filestore/parts.rs`, `counter.rs`): in the shared store, every writer commits size and parts together (its version stamp keeps older builds out), so a part missing there is lost. The transcript text (`output`) now reads it as blank, like a damaged part. An append onto it pads with spaces, not zeros, so the gap is never a line of NUL bytes. Binary files (`output.idx`, `output.tsidx`) and per-channel stores keep refusing such a read.
  - **The pane** (`useHistoryPagination.ts`, `HistoryLoadFailedBanner.tsx`): when srv answers "retry", it tries again after 1, 3 and 8 seconds; if it still fails, a notice says the earlier messages couldn't be loaded and why, that new messages still work, and that reopening the pane tries again.

**Prevention.**
1. **Upgrade SQLite to 3.51.3 or later:** `rusqlite` 0.31 → 0.39.0, which bundles `libsqlite3-sys` 0.37.0 with SQLite 3.51.3. It is a one-line change in `crates/srv/Cargo.toml`, the only rusqlite user.
   - **Checked so far:** it compiles cleanly, and the storage, migration, registry and saga tests pass on Linux.
   - **Behaviour to watch at runtime** (release notes 0.32 to 0.39): extended result codes; `execute` and `prepare` rejecting a trailing second statement; u64/usize bindings off by default.
2. **Shut vulnerable builds out of the shared store:** have the fixed build stamp the shared store with a schema version above 1. Older builds already refuse a newer schema version and fall back to their per-channel store (`stores.rs:382-385`).
3. **Stop the constant checkpointing:**
   - one checkpointer for the shared store per machine, not one per process;
   - trigger it on frames not yet checkpointed, not on the WAL file's size;
   - set `journal_size_limit`, with an occasional TRUNCATE.
4. **Treat SQLITE_CORRUPT as an incident:** tell the user, stop writing to the damaged zone (the per-channel copy keeps being written), and show the per-channel copy in history views. **Done in #5204** for appends, tail reads and index rebuilds, and the user hears at once; the resume, segment, summary, archive, snapshot, memory-record and Global Memory readers follow it; the Agent History list and the agent record follow it; fork history still only logs; a periodic `quick_check` is deliberately not built (decision, 2026-10-20): the shared store is 15 GB and every srv uses it, so neither a check on the live file nor a copy per check is practical; the first corrupt error is detected and reported instead (#5204, #5211, #5212, #5225, #5230), and the offline check on a copy is the recovery tool (#5206), run by the operator with every instance stopped.
5. **Keep `agent:transcriptsinglecopy` ("write each line once", #5176) off** until 1 to 4 land. It removes the per-channel copy, which is what recovery depends on.
