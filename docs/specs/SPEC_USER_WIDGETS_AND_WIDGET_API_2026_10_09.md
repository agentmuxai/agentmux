# User widgets and the widget API

**Status:** active — W1 (packages and approval, §13) in PR #4575; W2 to W6 not started.
**Date:** 2026-10-09
**Builds on:** `SPEC_PANE_TAB_CONTRACT_V1_2026_09_24.md` (the pane tab contract, and its Phase 6: user widgets as trusted local ES modules), `SPEC_HOST_API_SEAM_2026_09_26.md` (the host seam), `SPEC_WIDGET_DEFAULT_PANE_COLORS_2026_10_05.md` (`defaultHue`), `SPEC_AGENT_DRIVEN_BROWSER_PANES_2026_10_07.md` §5.6 (answers that only the host can give)
**Supersedes, for widgets:** `web-widget.md`, the plugin tiers in `docs/analysis/ANALYSIS_PLUGIN_WIDGET_MESSAGING_INTEGRATION_2026_06_24.md`, and the "community catalog, deferred" line of `SPEC_TOOLCHAIN_MANAGER_EXTERNAL_WIDGETS_2026_06_22.md`

## 1. Goal

Users can add their own widgets to AgentMux: a pane type of their own, in the widget bar, in the pane "+" picker and in tab presets, written against one documented, versioned API, with an SDK and samples that get a first widget running in minutes. A widget can be written by hand, generated by an agent, or installed from someone else, and in each case it can do only what the user allowed.

## 2. What exists today (main at 71d853a90)

User widgets already work, for a trusted author. Pane Tab contract v1, Phase 6 (#3767) shipped them:

| Piece | Where | Today |
|---|---|---|
| The contract | `frontend/app/block/pane-tab-registry.ts` (`PaneTabManifest` :138, `registerPaneTab` :178) | One registry for every pane type, built-in or not: `apiVersion: 1`, `view`, `label`, `icon`, `defaultHue`, `capabilities`, `create(ctx)` returning a `PaneTabInstance` (`component`, `liveTitle`, `headerActions`, `contextMenu`, `dispose`, …) |
| What a widget gets | `PaneTabHostContext` (`pane-tab-registry.ts:76`, built in `pane-tab-host.tsx:22`) | `blockId`, reactive `meta`, `setMeta(patch)`, `isFocused`, `visibility` |
| Where a user declares one | the user's `widgets.json`, next to `settings.json` (`crates/srv/src/backend/user_widgets.rs`) | Merged over the built-ins (new key adds, same key replaces), hot-reloaded, a parse error keeps the last good set. An entry with `"module": "<path>"` and `blockdef.meta.view: "ext:<name>"` is a user widget |
| How it loads | `frontend/app/block/widget-loader.ts` | Reads the module through the `readeditorfile` RPC, points its `solid-js` imports at the app's own Solid, imports it from a blob URL, validates the default export |
| Containment | `BlockErrorBoundary`, a caught `create` | A throwing widget shows an error pane, not a broken app |
| Sample | `docs/examples/widgets/hello/index.js` | Copy to `~/.agentmux/widgets/hello/`, add the `ext@hello` entry |
| Opening one programmatically | `pane.open` with `meta` (`rpc_types/block.rs:715`) | Generic: any view, including `ext:`, opens with the meta given |

**Decided (repo owner, 2026-09-24):** v1 loads trusted, locally installed ES modules only, with no sandbox; "a future marketplace or remote-loading story would revisit it." This spec is that revisit.

What v1 doesn't have: a package or manifest file (id, version, author, assets, permissions); a way to install, list, disable, update, reload or remove a widget in the UI (a loaded widget is never reloaded or unregistered until restart, `widget-loader.ts:182-187`); any isolation; widgets in anything but the app's own Solid version; agent tools beyond `pane.open`; contributions beyond panes (the status bar is a fixed list, `StatusBar.tsx:40-96`; the command palette takes built-ins only, `command-registry.ts`). `widgets.json` lives in the per-channel settings directory, while modules resolve against `~/.agentmux/widgets/`.

Stale docs to fix in W1: the Pane Tab spec's status line says terminal and agent aren't started (its body says they are); `SPEC_SETTINGS_WIDGET.md` and `widget-visibility-rearchitecture.md` disagree about whether a user `widgets.json` exists; `app-api-extension.md` is "Proposed" but built.

Other prior art that stays: messenger widgets and Toolchain's "Open Pane" are `widgets.json` entries for a browser pane at a URL (`view: "browser", url`); `widget.api` (`cli_handlers.rs:593`) is a loopback-only HTTP proxy for local tools.

## 3. Decisions

Recommendations accepted by the repo owner on 2026-10-09 ("use best recommendations"):

1. **Sandboxed is the default kind; trusted is an opt-in** that the user confirms in plain words.
2. **Trusted widgets stay a supported kind**, for built-in-grade widgets and for development, behind that confirmation.
3. **Widget files are served by srv on its main port**, at a dedicated read-only route (§5.2). It works on every host, a browser-hosted AgentMux included.
4. **`agents:send` is in the API**, in the last runtime phase (W3), and its install prompt says what it means.
5. **One packages folder for every channel**, `~/.agentmux/widgets/`; approvals are kept per AgentMux instance, so a dev build asks again.
6. **Publisher ids are free-form** (`<publisher>.<name>`) until there's a catalog.

## 4. Concepts

- **Widget package:** a folder in `~/.agentmux/widgets/<id>/` with a `widget.json` manifest and the widget's files.
- **Kind:** `sandboxed` (runs in an iframe, reaches AgentMux only through the bridge) or `trusted` (a Solid ES module in the app's renderer, the v1 model).
- **Pane contribution:** a pane type the package adds. Its view name is `ext:<id>/<name>`. One package may contribute several.
- **Bridge:** the message protocol between a sandboxed widget's iframe and AgentMux (§6).
- **SDK:** `@agentmux/widget-sdk`, the JavaScript client for the bridge (§7).
- **Permission:** a named capability the manifest asks for and the user grants at install (§6.4).
- **Approval:** the user's install decision, recorded by srv against the package's content hash (§8).

## 5. The package

### 5.1 Layout

```
~/.agentmux/widgets/acme.pr-dashboard/
  widget.json      the manifest (required)
  index.html       a sandboxed widget's entry document
  app.js, app.css  its scripts and styles (any names, any subfolders)
  icon.svg         optional
```

A trusted package has `index.js` (or whatever `entry` names) instead of `index.html`. Limits: 50 MB and 2,000 files per package; no symlinks (a package with one is invalid).

### 5.2 How files are served

srv serves an approved, enabled package's files read-only at:

```
GET /agentmux/widget-files/<id>/<content-hash>/<key>/<path>
```

- Only files inside the package folder; `..`, absolute paths and symlinks are refused. The `<content-hash>` segment must equal the approved hash (§8.2), so a URL always means one exact version of the code. Each file is hashed again on every read and compared with its hash at approval, so an edited file is never served (409), whether or not srv's folder watcher noticed the edit.
- No auth key: the URL is what the iframe loads, and package files aren't secrets. `<key>` is an HMAC of the instance secret over the id and hash (srv hands the full URL to the UI in `widgets.list`), so a web page elsewhere on the machine can't name a package's files.
- Every response carries `Content-Security-Policy` (§6.1), `X-Content-Type-Options: nosniff`, `Cache-Control: no-cache`, `Referrer-Policy: no-referrer` and a content type from the extension.
- The SDK is served the same way at `GET /agentmux/widget-sdk/v1.js` (§7).

### 5.3 The manifest, `widget.json`

```json
{
  "manifestVersion": 1,
  "id": "acme.pr-dashboard",
  "name": "PR Dashboard",
  "version": "1.2.0",
  "description": "Open pull requests across your repos",
  "author": "Acme",
  "homepage": "https://example.com/pr-dashboard",
  "icon": "code-pull-request",
  "defaultHue": 210,
  "kind": "sandboxed",
  "entry": "index.html",
  "permissions": ["storage", "net:https://api.github.com"],
  "minAgentMux": "0.60.0",
  "contributes": {
    "panes": [
      { "name": "main", "label": "PRs", "icon": "code-pull-request", "entry": "index.html", "defaultMeta": {} }
    ]
  }
}
```

| Field | Type | Required | Meaning |
|---|---|---|---|
| `manifestVersion` | integer | yes | The package format; this spec is `1`. AgentMux refuses a version it doesn't know, with a message naming both. |
| `id` | string | yes | `<publisher>.<name>`: lowercase letters, digits and `-`, one dot, at most 64 characters (`^[a-z0-9-]+\.[a-z0-9-]+$`). Must equal the folder name. Namespaces views, storage and meta keys. |
| `name` | string | yes | Shown in the install prompt and Settings. At most 60 characters. |
| `version` | string | yes | Semver (`1.2.0`). |
| `description` | string | no | One or two sentences, at most 300 characters. |
| `author`, `homepage` | string | no | Shown in the prompt. `homepage` must be `https:`. |
| `icon` | string | no | A Font Awesome name (as built-in widgets use), or a path to an SVG/PNG in the package. |
| `defaultHue` | integer 0–359 | no | The pane color hue, as `SPEC_WIDGET_DEFAULT_PANE_COLORS`. |
| `kind` | `"sandboxed"` \| `"trusted"` | no, default `"sandboxed"` | §4. |
| `entry` | string | no | The default entry for panes that don't name one: `index.html` (sandboxed) or `index.js` (trusted). |
| `permissions` | string[] | no | §6.4. Unknown names make the package invalid. Ignored for `trusted` (it has full access). |
| `minAgentMux` | string | no | The lowest AgentMux version the widget works with; an older AgentMux lists it as needing an update. |
| `contributes.panes` | object[] | yes, at least one | Each: `name` (`^[a-z0-9-]+$`, the part after `/` in the view name), `label`, optional `icon`, `entry`, `defaultMeta` (merged into a new pane's meta, keys under `widget:` only), `singleton` (bool: a click focuses the open pane instead of adding one). |
| `contributes.commands`, `contributes.statusItems` | | reserved | W5. Ignored until then; not an error. |

**Validation** happens in srv when it scans the folder (§8.1). An invalid package is listed in Settings with its first error ("`version` isn't semver"), never loaded.

### 5.4 Placement

Installing a package adds a widget-bar entry for each pane, keyed `ext@<id>/<name>`, unpinned: it appears in the "+" picker and under **more** in the widget bar, and the user pins it like any widget. The user's own `widgets.json` can still rename, reorder, hide or replace the entry, as today. A tab preset can name it (`{"widget": "ext@acme.pr-dashboard/main"}`).

### 5.5 v1 widgets

A `widgets.json` entry with `module` and an `ext:<name>` view keeps working: srv treats it as a trusted package with an implied manifest (id `local.<name>`, version `0.0.0`, its one module as the entry). It needs the user's confirmation once, like any trusted package (§8). The `hello` sample gets a `widget.json`, so it installs like any other.

## 6. The bridge (sandboxed widgets)

### 6.1 The sandbox

The pane's host side (a pane tab manifest srv-backed for each sandboxed contribution) renders:

```html
<iframe sandbox="allow-scripts allow-forms allow-modals allow-downloads"
        src="/agentmux/widget-files/<id>/<hash>/<entry>?pane=<nonce>"
        allow="clipboard-write"></iframe>
```

- **No `allow-same-origin`:** the document has an opaque origin. It can't read the app's DOM, `localStorage`, cookies, `window.api`, the srv auth key or the host IPC token, and every request it makes carries `Origin: null`, which srv's CORS refuses.
- **No `allow-top-navigation` or `allow-popups`:** it can't navigate the app or open windows. Links go through `ui.openUrl` (§6.3).
- **CSP on every widget file:** `default-src 'none'; script-src 'self' 'unsafe-inline' 'unsafe-eval' blob:; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:; font-src 'self' data:; media-src 'self' blob:; connect-src 'none'; frame-src 'none'; form-action 'none'; base-uri 'none'`. `'self'` is the widget files route. A widget loads code only from its own package and reaches the network only through `net.fetch`.
- **Navigation is fatal:** the host counts the iframe's `load` events. A second one (the widget navigated itself, or was navigated) closes its bridge port at once and shows "This widget left its page and was stopped. Reload it." The port is never handed to a document it didn't load.

### 6.2 Connecting

1. The host creates the iframe and waits for its first `load`.
2. The host creates a `MessageChannel` and posts `{ "type": "agentmux:connect", "protocols": [1] }` to the iframe's window with `port2` transferred. (Target origin `*` is required for an opaque origin; the navigation rule above is what keeps the port with the right document.)
3. The widget answers on the port with the `hello` request (§6.3). Until it does, nothing else is accepted; a widget that hasn't said hello in 10 s is shown as failed to start.
4. All further traffic is on the port, never `window.postMessage`.

Messages are JSON-RPC 2.0. A request: `{"jsonrpc":"2.0","id":7,"method":"meta.set","params":{"patch":{"filter":"open"}}}`. A result: `{"jsonrpc":"2.0","id":7,"result":{}}`. An error: `{"jsonrpc":"2.0","id":7,"error":{"code":1001,"message":"…","data":{"permission":"storage"}}}`. The host's notifications have no `id`: `{"jsonrpc":"2.0","method":"visibility","params":{"state":"dormant"}}`.

Limits: one message at most 32 MB (base64 file data included); at most 64 requests in flight per pane; the host answers every request (a timeout is an error, never silence).

### 6.3 Methods

Methods marked "—" in the permission column need none.

| Method | Params | Result | Permission |
|---|---|---|---|
| `hello` | `{ protocol: 1, sdk?: string }` | `{ protocol: 1, widget: { id, version, pane }, agentmux: { version, host }, permissions: string[], theme: Theme, meta: object, visibility, focused }` | — |
| `meta.get` | `{}` | `{ meta: object }` | — |
| `meta.set` | `{ patch: object }` (a `null` value deletes the key) | `{}` | — |
| `ui.setTitle` | `{ text: string, icon?: string }` | `{}` | — |
| `ui.setHeaderActions` | `{ actions: { id, icon, title }[] }` (at most 4) | `{}` | — |
| `ui.setContextMenu` | `{ items: ({ id, label, disabled? } \| { separator: true })[] }` (at most 20) | `{}` | — |
| `ui.toast` | `{ text: string, kind?: "info"\|"success"\|"warning"\|"error" }` | `{}` | — |
| `ui.openUrl` | `{ url: string }` (`http:` or `https:`) | `{}`: opens a browser pane next to the widget | — |
| `theme.get` | `{}` | `Theme` | — |
| `panes.open` | `{ view: string, meta?: object, split?: "right"\|"down"\|"tab" }` | `{ pane: string }` | — for the package's own views; `panes` for any other view |
| `storage.get` | `{ key: string }` | `{ value: any \| null }` | `storage` |
| `storage.set` | `{ key: string, value: any }` (JSON) | `{}` | `storage` |
| `storage.delete` | `{ key: string }` | `{}` | `storage` |
| `storage.list` | `{ prefix?: string }` | `{ keys: string[] }` | `storage` |
| `net.fetch` | `{ url, method?: string, headers?: object, body?: string, bodyBase64?: string, timeoutMs?: number }` | `{ status, statusText, headers: object, body?: string, bodyBase64?: string, url }` (`body` for text types, `bodyBase64` otherwise) | `net:<origin>` matching `url` |
| `files.pick` | `{ accept?: string[], multiple?: boolean }` | `{ files: { name, type, size, dataBase64 }[] }` | `files` |
| `files.save` | `{ name: string, type?: string, dataBase64: string }` | `{ saved: boolean }` | `files` |
| `clipboard.writeText` | `{ text: string }` | `{}` | `clipboard:write` |
| `agents.list` | `{}` | `{ agents: { id, name, provider, state: "working"\|"idle"\|"stopped" }[] }` | `agents:read` |
| `agents.send` | `{ agent: string, text: string }` | `{ id: string }` | `agents:send` |

Details:

- **`meta`** is the pane's own meta, under the widget's namespace: the widget sees and writes `filter`, srv stores `widget:<id>:filter`. Other meta keys are invisible to it. At most 64 KB per pane. Meta survives restarts and moves with the pane, like any pane's.
- **`storage`** is per package, not per pane: srv keeps it in its database, at most 5 MB per package, values up to 1 MB each. Uninstalling deletes it after the user confirms.
- **`net.fetch`** is made by srv, not the iframe: no cookies, no credentials of the user's browser profile, no `Origin` header of AgentMux. The request URL's origin must match one of the package's `net:` permissions exactly (`net:https://api.github.com` allows that origin and nothing else; `net:https://*.example.com` allows its subdomains, never the bare wildcard). Redirects are followed only to allowed origins. Loopback (`127.0.0.1`, `localhost`, `::1`) and private addresses are refused unless the permission names that exact origin, port included (`net:http://127.0.0.1:8188`). Responses up to 10 MB; default timeout 30 s, at most 120 s.
- **`files.pick`** opens the host's file dialog; the widget gets the chosen files' contents (up to 25 MB in all), never a path. A cancelled dialog is error `1006`. `files.save` opens a save dialog; `saved: false` if cancelled.
- **`agents.send`** delivers `text` to one of the user's own agents on this machine, as a message marked as sent by the widget (`FROM=widget:<id>`, `TRUST=self-declared`), which the agent treats like any unverified message. At most 10 messages a minute per package, 8 KB each.
- **`ui.setHeaderActions` / `ui.setContextMenu`** are drawn by AgentMux, in its own style; a click comes back as the `action` event.

`Theme` is `{ mode: "dark" | "light", vars: { [name: string]: string } }`: the app's colors as CSS custom properties (`--am-bg`, `--am-fg`, `--am-muted`, `--am-accent`, `--am-border`, `--am-error`, `--am-warning`, `--am-success`, `--am-font`, `--am-font-mono`, `--am-radius`, plus the pane's hue as `--am-pane-hue`). The SDK applies them to the document (§7).

### 6.4 Permissions

| Permission | What the install prompt says |
|---|---|
| `storage` | "Keep its own data on this computer" |
| `net:<origin>` | "Connect to `<origin>`" (one line per origin) |
| `files` | "Open files you pick, and save files where you choose" |
| `clipboard:write` | "Copy text to your clipboard" |
| `panes` | "Open other kinds of panes" |
| `agents:read` | "See your agents' names and whether they're working" |
| `agents:send` | "**Send messages to your agents.** An agent acts on what it's told, so only allow this for a widget you trust." |

A trusted package's prompt has one line instead: "**This widget runs as part of AgentMux, with full access to everything AgentMux can do.** Only install it if you trust its author."

### 6.5 Events

| Event | Params | When |
|---|---|---|
| `visibility` | `{ state: "active" \| "dormant" \| "windowHidden" }` | The pane's tab is shown, hidden behind another tab, or its window is minimized |
| `focus` | `{ focused: boolean }` | The pane gains or loses focus |
| `theme` | `Theme` | The user changes theme or the pane's color |
| `meta` | `{ meta: object }` | The pane's widget meta changed from outside the widget (another window, an agent, an undo) |
| `action` | `{ id: string, source: "header" \| "menu" }` | The user clicked one of its header actions or menu items |
| `dispose` | `{}` | The pane is closing or the widget is being reloaded; the port closes 1 s later |

A dormant widget keeps running (it's an iframe), but should pause timers and polling; the SDK makes that one line.

### 6.6 Errors

| Code | Name | When |
|---|---|---|
| -32700, -32600, -32601, -32602 | JSON-RPC parse, invalid request, method not found, invalid params | As JSON-RPC defines |
| 1001 | `permission_denied` | The package wasn't granted what the method needs; `data.permission` names it |
| 1002 | `limit_exceeded` | A size, count or rate limit; `data.limit` names it |
| 1003 | `not_found` | An unknown agent, view or storage key |
| 1004 | `network_error` | `net.fetch` failed before a response (DNS, refused, timeout, a disallowed redirect) |
| 1005 | `unavailable` | This host can't do it (`files.pick` on a host without dialogs) |
| 1006 | `cancelled` | The user cancelled a dialog |
| 1007 | `not_ready` | A request before `hello` |
| 1099 | `internal` | AgentMux failed; `message` says how |

### 6.7 Versioning

- The **protocol** version is negotiated in the handshake. Within protocol 1, AgentMux only adds: new methods, new optional params, new result fields, new events. A widget ignores fields it doesn't know. Anything else is protocol 2, and AgentMux keeps speaking 1 for at least a year after 2 ships.
- The **manifest** format has its own `manifestVersion`, with the same additive rule.
- A widget can check what's there: `hello` returns `agentmux.version` and the granted `permissions`; calling an unknown method returns `-32601`, never a crash.

## 7. The SDK, `@agentmux/widget-sdk`

One ES module with TypeScript types, no dependencies, about 5 KB. Served by srv at `/agentmux/widget-sdk/v1.js`, so a widget with no build step can `import` it, and also published to npm for widgets built with a bundler.

```js
import { connect } from "/agentmux/widget-sdk/v1.js";

const am = await connect();           // the handshake; applies the theme
am.ui.setTitle("PRs");
am.on("visibility", ({ state }) => (state === "active" ? start() : stop()));
am.on("action", ({ id }) => id === "refresh" && refresh());
await am.ui.setHeaderActions([{ id: "refresh", icon: "rotate", title: "Refresh" }]);

const res = await am.net.fetch("https://api.github.com/search/issues?q=is:pr+is:open+author:@me");
const data = JSON.parse(res.body);
await am.storage.set("lastCount", data.total_count);
```

| Export | Does |
|---|---|
| `connect(options?)` | Waits for `agentmux:connect`, sends `hello`, returns an `AgentMux` client. `options.applyTheme` (default `true`) sets the theme's CSS variables on `document.documentElement` and keeps them current; `options.timeoutMs` (default 10,000). Rejects with a clear message when the page isn't running inside AgentMux. |
| `AgentMux` | `info` (the `hello` result), `on(event, cb)` → unsubscribe, `call(method, params)` for anything without a wrapper, and one namespace per area: `meta`, `ui`, `theme`, `panes`, `storage`, `net`, `files`, `clipboard`, `agents`, each method returning a promise. |
| `AgentMuxError` | Thrown on an error response: `code`, `name` (`permission_denied`, …), `message`, `data`. |
| `useVisibility(am, { onActive, onDormant })` | The pause-when-hidden helper. |
| `base64` | `encode(bytes)`, `decode(text)`, for files and binary fetches. |

The SDK's `.d.ts` is the typed form of §6; its tests are the protocol conformance tests, run against a fake host.

**`am-widget.css`** (served next to the SDK, optional): a small stylesheet that uses the theme variables for body text, buttons, inputs, lists and code, so a plain-HTML widget looks at home with no CSS of its own.

## 8. Installing and approval

### 8.1 Discovery

srv scans `~/.agentmux/widgets/` at start and watches it. For each folder it parses and validates `widget.json` (§5.3), computes the content hash (§8.2), and reads the instance's approval record. A package's state is one of:

| State | Meaning | Loads? |
|---|---|---|
| `approved` | Approved, and its hash still matches | yes, unless disabled |
| `needs_approval` | New, never approved here | no |
| `changed` | Approved once, but its files changed since | no, until approved again |
| `invalid` | Its manifest or files break a rule (§5); `error` says which | no |
| `disabled` | Approved, turned off by the user | no |

### 8.2 The content hash

Each file's SHA-256 (hex), then SHA-256 over the files sorted by relative path: for each, the path, a NUL byte, the file's hash, a newline. Any change to any file (an edit, an update, a file added) changes it. The per-file hashes are kept with the approval, for the check on every read (§5.2).

### 8.3 Approval

- A package loads only once the user has approved it **in AgentMux's own UI**, never because files appeared on disk.
- The prompt shows the name, author, version, kind, and each permission in the words of §6.4. Buttons: **Install** and **Cancel**. For a `changed` package whose permissions are unchanged and that is sandboxed, the prompt is shorter ("PR Dashboard was updated to 1.3.0"); a trusted package always gets the full prompt, since its code is its access.
- **The user's answer reaches srv only through the host:** the frontend calls a host command, and the host posts the answer to srv with its own token, which srv checks (the browser pane approval route, `/api/v1/host/browser_attention`, is the model). The instance auth key, which every agent has, can't approve anything.
- srv records `{ id, hash, kind, permissions, approved_at }` per instance (in its data directory, not in the shared widgets folder), and removes the record when the package is uninstalled.

### 8.4 The Widgets section in Settings

Settings → **Widgets** lists every package: icon, name, version, kind, state, permissions, and its last load error if any. Actions: **Approve** (for `needs_approval` and `changed`), **Enable** / **Disable**, **Reload**, **Show folder**, **Uninstall** (asks first; deletes the folder, its approval and its storage). At the top: **Install from folder…** and **Install from .zip…**, which validate, copy into `~/.agentmux/widgets/<id>/` (asking before replacing an existing version) and open the approval prompt.

**Development:** **Load from folder (development)** points at a folder anywhere, watches it, and reloads open panes on every change. It's approved once per folder; while it is loaded, its panes say "development" in the header. A sandboxed development widget still gets only its granted permissions; a changed manifest asks again.

### 8.5 Reload

Reloading a package (after an update, an edit in development, or the user's **Reload**) sends `dispose` to its open panes, unregisters its pane types, registers the new ones, and remounts the panes with their meta. The registry needs `unregisterPaneTab` for this; today `registerPaneTab` throws on a taken name and the loader never reloads.

## 9. Trusted widgets

A trusted package's entry is v1's ES module: its default export is a `PaneTabManifest` (the Pane Tab contract, `apiVersion: 1`) for its one pane, or an object `{ panes: { <name>: PaneTabManifest } }` for several. The loader keeps pointing `solid-js` imports at the app's own Solid. The module is fetched from the widget files route (§5.2), so it can only be the approved code. The Pane Tab `apiVersion` stays the Solid-coupled contract version: AgentMux bumps it only when the shared Solid version or the contract breaks, and lists a trusted widget built for another version as needing an update.

## 10. Agents

Agents can build widgets for the user and open them:

| MCP tool | Params | Does |
|---|---|---|
| `WidgetList` | — | Installed packages: id, name, version, kind, state, permissions, views |
| `WidgetInstall` | `{ path: string }` (a folder or `.zip` in the agent's workspace) | Validates and copies the package and asks the user to approve it (§8.3); returns once they answer: `installed`, `cancelled`, or the validation error |
| `OpenWidget` | `{ view: string, meta?: object, split?: "right"\|"down" }` | Opens a pane of an installed, approved widget next to the agent's pane |

An agent can't approve its own install or raise a widget's permissions; every install is the user's decision in the prompt. A workspace skill, "Write an AgentMux widget", gives agents the manifest rules, the SDK and the samples, and the test loop (`WidgetInstall`, `OpenWidget`, read the pane's error, fix, install again).

## 11. Security summary

- A sandboxed widget holds no credential: no auth key, no host token, no session. Everything it does is a bridge call the host checks against its grants, and srv checks again for every call that reaches srv (storage, net, agents), using a token scoped to that widget and pane: srv issues it when the pane opens, its route allowlist accepts it only on the widget routes, and it names the package id, the approved hash and the granted permissions (the scoped container credential, `container_route_allowed` in `auth.rs`, is the model).
- Its code comes only from its approved files (CSP, and the hash in every file URL).
- A trusted widget has full access by design, and the prompt says so in those words.
- No code runs without the user's approval in AgentMux's own UI, and only the host can carry that approval to srv.

## 12. What this doesn't do

- No VS Code-style extension host, no editor extensions (deferred indefinitely in `SPEC_EDITOR_FILE_TREE_2026-05-26.md`).
- No remote code: a widget is files on this machine. It can fetch data from origins it declared, not code (CSP).
- No widget processes. A widget that needs a backend talks to a local tool on a port (the Toolchain pattern), through `net:http://127.0.0.1:<port>`.
