**Author:** Lark

## 0. TL;DR

1. **Summary line.** Each agent-related toast gets a small third line with the agent's current Haiku session summary (block meta `term:ambient_summary`, e.g. *"Fix resize repaint delay in terminal panes"*). On Windows it goes in the toast's `attribution` slot, which renders small and grey under the body. On Linux it is appended as the last body line. It goes through the same sanitize, redact and "notification content" rules as the question text. If an agent has no summary yet, the line is left out.
2. **"has a question".** The `InputWaiting` title becomes **"{agent} has a question"**. The first question's text is the subtext (line 2), and the summary is line 3. If the agent asked more than one question, a suffix says "(+N more)".
3. **Click → pane, made reliable.** Clicking works today only in the easy case. §3.2 lists **seven** cases where a click does nothing or does the wrong thing. The fix:
   - srv resolves which window owns the block;
   - only that window reacts;
   - the launcher raises the window itself while it still holds the click's foreground rights;
   - minimized windows are restored;
   - the pane gets real DOM focus;
   - with no window open, a window is opened **on the block's workspace**.

## 1. Summary line

### 1.1 What exists (verified)

- **Source:** block meta **`term:ambient_summary`**. It is a PR-title-style description of the session's overall goal, generated by `claude-haiku-4-5` through srv's `register_session_activity_summary` (`agentmux-srv/src/server/app_api/session.rs:767-866`; prompt at `:972-993`) and sanitized by `sanitize_ambient_text` (`:1237`).
- **Who writes it:** the frontend (`frontend/app/view/agent/hooks/useAgentActivitySummary.ts:80-123`, via `ObjectService.UpdateObjectMeta`), once per user submission.
- **Length:** clamped to 5–12 words (srv allows 3–20, default 7). No punctuation. Stable across turns unless the goal changes.
- **When it is cleared:** when the agent process exits (`useBlockActivity.ts:44-52`).
- **Where it is shown today:** only the Swarm view (`swarm-model.ts:1950` → `readActivitySummary()`, which falls back to `term:osc_title`). It was removed from the pane header on 2026-09-20.
- **Reading it in srv:** a blocking SQLite read of the block (`store.get::<Block>` then `meta_get_string(.., "term:ambient_summary", "")`). The Router already does this same fetch for `agentName` inside `spawn_blocking` (`router.rs:456-485`).

**Known gaps in the source** (verified 2026-09-25):
- **Generation needs the pane mounted.** In practice that is almost always true: every tab of a window's workspace stays mounted, and inactive tabs are only hidden (`workspace.tsx` renders all of `allTabIds()`). A pane is unmounted only in **background mode** (every window closed while the tray keeps agents running) or when its workspace is open in no window. In those cases the agent has no summary, or a stale one.
- **It only refreshes on the user's own messages.** It is triggered by a user submission in the pane (`TurnPhase: Submitting`, non-hidden). Turns started by jekts, cron, CI results or other agents don't refresh it, so it describes what the user last asked, which may lag what the agent is doing now.

**Decision (repo owner, 2026-09-25): keep it simple.** Use the pane-generated `term:ambient_summary` as-is and leave the line out when there isn't one. How background agents work, including srv-side summaries, will be designed separately later. This spec does not change generation (§1.5).

### 1.2 Design

- **Read point:** `Router::emit` and `emit_fixed` already fetch the `Block` for the agent name. The same fetch returns `term:ambient_summary` too. There is no extra query, and it stays inside the existing `spawn_blocking` (the #1782 rule).
- **Caching:** the name cache is kept. The summary is **not** cached, because it changes every turn. The lookup happens once per emit, and emits are rare.
- **Payload:** `OsNotification` gains `summary: Option<String>`. The ts-rs binding is regenerated.
  - On the launcher side the field gets `#[serde(default)]`. The launcher already ignores unknown fields, so srv can ship first.
- **Sanitizing, in order:**
  1. Strip control and bidi characters (the same filter as `sanitize_name`).
  2. Collapse whitespace to a single line.
  3. Cap at **90 characters** with a trailing `…`.
  4. If `is_sensitive_message(summary)` matches (the jekt tier-gate keyword list), **drop** the line entirely rather than show "sensitive content". The summary is decoration, not information the user needs.
  5. `notify:os:preview = "none"` drops it, as it does the body.
- **Which kinds get it:** `InputWaiting`, `TurnCompleted`, `TurnErrored`, `AgentCrashed` and `MessageNeedsReview`. **Not** `Summary` (no block) and not `Test`.
- **Fallback:** when `term:ambient_summary` is empty, use nothing.
  - `term:osc_title` (the Swarm fallback) is **not** used. It is terminal-controlled text from the agent CLI, which is less trustworthy for an OS surface.
  - srv's continuity-state `## Current goal` would be an srv-owned source that works without a window, but only for Claude, and only every 3 turns or 10 minutes. It is noted as a possible follow-up in §1.5, not used in v1.
- **Setting:** `notify:os:summary` (bool, default `true`) in Settings → Notifications & Tray: "Show what the agent is working on".
- **Duplicate reports** (the idempotent same-question branch, `policy.rs:383-388`) fill a missing `summary` just as they fill a missing `body`.

### 1.3 Rendering

**Windows** (`agentmux-launcher/src/notify/windows.rs::build_xml`):
- The skeleton gains an optional `<text placement="attribution"/>`, filled with `CreateTextNode` like the other lines. Nothing from an agent is ever parsed as XML (the existing hostile-text test is extended to cover the summary).
- `attribution` renders smaller and in a secondary color under the body. That is the "sub-section" look the request asks for, and it does not use up one of the three `<text>` slots in ToastGeneric.
- Parent spec §6.1 reserved `attribution` for provenance ("via ReAgent · verified"). The only kind that would need provenance, `ReviewArrived`, isn't built. **Rule:** a kind that needs provenance gets it in `attribution`, and its summary moves to the third body `<text>` instead.

**Linux** (`notify/linux.rs::texts`): append `"\n" + summary` to the body. It is escaped the same way as the body when the server supports markup. There is no attribution slot. Some servers (e.g. GNOME) show only the first lines of a body; that is accepted.

**Tray menu:** unchanged (titles only). The summary is not shown there.

### 1.4 Example

```
┌─────────────────────────────────────────────┐
│ [AgentMux icon]  AgentMux                    │
│ lark has a question                          │  ← title (app template)
│ Which branch should I target for the fix?    │  ← question (subtext)
│ Fix resize repaint delay in terminal panes   │  ← summary (attribution: small, grey)
└─────────────────────────────────────────────┘
```

### 1.5 Out of scope / follow-ups

- Generating the summary on srv so it works with no pane mounted: either move the `useAgentActivitySummary` trigger into srv's turn-start path, or use continuity state's `## Current goal` for Claude. That is a separate change to the ambient-calls path, with its own cost and privacy review.
- The dead `agent:summary` 20 s Haiku loop (`reactive/activity_watcher.rs`) should be removed on its own merits: nothing reads it, and it costs Haiku calls. Not part of this spec.

## 2. "Agent has a question"

### 2.1 Change

- `policy::title_for(InputWaiting)` changes from `"{agent} needs your input"` to **`"{agent} has a question"`**.
- The tray's attention menu item uses the same title, since it is the same template.
- **Subtext (line 2)** is the first question's text: `questions[0].question`, from either srv's `can_use_tool` frame (`sources.rs`) or the renderer (`useAgentQuestions.ts`). It goes through the existing `redact_body` rules:
  - first line only;
  - 80 characters (200 with `preview=full`);
  - replaced with "Contains sensitive content — open AgentMux to view." when it matches a keyword;
  - dropped when `preview=none`.
- **Several questions:** when `questions.len() > 1`, append ` (+N more)` *after* truncation, so the count is always visible. `sources::ask_user_question` and the renderer's `waiting-for-input` event start carrying `question_count`.
- **No question text available** (a malformed frame, or preview=none): the title stands alone. It no longer needs a body to make sense, which "needs your input" did.
- **Unchanged:** the `InputWaiting` kind, its attention priority, its taskbar flash, and the "Agent needs input" settings row. The settings row is relabelled **"Agent has a question"** to match.

### 2.2 Why not put the question in the title

The title is the one line an attacker would want to control (parent spec §9.1). It stays an app template with only the sanitized agent name inserted. The question stays in the body, where the rest of the §9.2 redaction already applies.

## 3. Click → the agent's pane

### 3.1 Current path (verified)

1. The toast click fires `Activated` in the launcher (`notify/windows.rs:195-206`). It calls `AllowSetForegroundWindow(ASFW_ANY)` and sends `UserAction::Clicked`.
2. The launcher sends `notify.ack {clicked:true}` to srv. The Router publishes `notification:activate {block_id}` with **no scope**, to every window.
3. **Every** frontend window runs `activateBlockLocally` (`os-notify-bridge.ts:89-112`):
   - it searches **only its own workspace** for the block;
   - then `setActiveTab`;
   - then `focusNode`, retried up to 10 × 50 ms;
   - then `raiseThisWindow` → host `focus_window` → UI-thread `window.activate()`.

### 3.2 Where it fails today

| # | Case | What happens now |
|---|---|---|
| F1 | The block's workspace isn't open in any window | No window finds it, so **nothing happens** and nothing is logged. `pending_activation` isn't used because a window exists. |
| F2 | No window open (background mode) | The launcher opens a **new empty workspace** window (`open_new_window` takes no arguments). `takeactivation` searches that empty workspace, so the window opens on the default layout, **not the pane**. |
| F3 | The window is minimized | The Views path relies on `window.activate()` alone. Restoring is likely but not explicit; the floater path does `IsIconic` → `SW_RESTORE` itself. |
| F4 | Foreground rights | The raise happens last, in the **host** process, after a long WebSocket → srv → broker → renderer → IPC chain. The launcher's `ASFW_ANY` grant may already be lost, or may never have been held for an unpackaged in-process activation (not verified live). If it fails, Windows only flashes the taskbar button. |
| F5 | The pane is already the tab's focused node | `focusNode` returns early (`layoutFocus.ts:152-153`), so `giveBlockFocus` never runs and the caret isn't moved into the pane. |
| F6 | Two windows share a workspace | Both switch tab and raise, and the last one wins. |
| F7 | A toast from before an srv respawn, or a "N more updates" summary toast | The unknown id is ignored, and a summary toast has an empty `block_id`, so **nothing happens**, not even a raise. |

### 3.3 Design

**A. srv resolves the target.** On `Ack{clicked}`, the Router's blocking task calls `service::resolve_agent_context(&mstore, block_id)`, which walks block → tab → workspace → window (`introspect.rs:174-217`, already used by the MCP tools). The result travels in two places:
- **`notification:activate`** payload gains `{ window_id?, workspace_id, tab_id }`.
- **The `notify.ack` response** to the launcher gains `{ window_id?, workspace_id }`. It keeps `has_window`, which now means "is `window_id` open", not "is any window open".

**B. Only the owning window reacts.** In `os-notify-bridge.ts`:
- A window acts only if its own `windowId` equals `window_id` (fixes F6).
- It `setActiveTab(tab_id)` directly, instead of searching tabs.
- If `window_id` is absent (the workspace is open nowhere), no window acts; that is F1, handled by (D).

**C. The launcher raises the window itself.** It is the process the click activated, so it is the most likely to hold foreground rights (fixes F4).
- On the ack response it maps `window_id` → host window label → HWND. The launcher's WRR mirror (`WindowMirror.hwnd`, keyed by label) already tracks every window's HWND. The window-id ↔ label pairing comes from the host's `BackendWindowIdRegistered` report, which the launcher can record next to the label.
- Then: `if IsIconic(hwnd) { ShowWindow(SW_RESTORE) }` (fixes F3), then `SetForegroundWindow(hwnd)`.
- If `SetForegroundWindow` returns false, it falls back to `AllowSetForegroundWindow(host_pid)` + the host `focus_window` IPC. If that fails too, it calls `FlashWindowEx`, which is Windows' own fallback, so the user at least sees where to go.
- The frontend still does the tab/pane selection (B). The raise no longer waits for it: raising first is what keeps the foreground grant usable.
- `raiseThisWindow` in the frontend stays as a no-op-safe second attempt.

**D. Opening the right workspace when needed** (fixes F1 and F2):
- When `has_window` is false (the target window isn't open, or no window is open), the launcher sends the host `open_new_window` **with** `{ workspace_id }`.
  - This needs a new argument on the launcher's `forward_host_cmd`, which today sends `{"cmd"}` only.
  - The host's window creation already accepts an existing `workspaceId` for reattach (`init/pool.ts`), so the new window loads **that** workspace.
- The new window then calls `notify.takeactivation`. It now returns `{block_id, tab_id, at_ms}` and is **ignored after 30 s** (fixes the "jumps to an old block much later" issue).
- **If the workspace no longer exists** (`window_close.rs` deletes a workspace when its last window closes): the Router falls back to creating a tab for the block in the new window's workspace. This is the same path MCP `OpenAgent` / `pane.moveTab` uses to re-home a block. Whether a workspace-less block is still openable must be confirmed in implementation; if it isn't, the toast click raises the new window and shows an in-app bubble: "That agent's pane was closed."

**E. The pane really gets focus** (fixes F5). After `setActiveTab` and `focusNode`, call `focusManager` → `giveBlockFocus(blockId)` unconditionally, so the caret lands in the agent pane's composer even if it was already the focused node.

**F. Clicks never do nothing** (fixes F7):
- A **summary toast** click raises the most recently focused window (no pane selection).
- The launcher **clears its toasts on `update_endpoint`** (srv respawn), because the new Router doesn't know their ids.
- An **unknown id** ack returns `{known:false}`, and the launcher still raises the most recently focused window instead of doing nothing.

**G. Nothing fails silently.** Replace the bridge's `.catch(() => {})` on the activation path with a `console.warn` plus a `fe_log_structured` line, and log every branch of (C)/(D) in the launcher, so "clicked and nothing happened" can be diagnosed from logs.

### 3.4 Security

- The `window_id`, `workspace_id` and `tab_id` in the activation payload are resolved by srv from its own notification record, never taken from the toast's `launch` argument.
- Parent spec §9.3 still holds: activation only focuses and opens things, and never runs anything.
- `open_new_window {workspace_id}` accepts only an id srv resolved for this click.

## 8. As built (2026-09-25)

- **§1.2 name cache removed, not kept.** The summary can't be cached and needs a block read on every emit; that same read returns the name, so the cache saved nothing (#3732).
- **"Open" is a connected frontend, not a `Window` row.** `notify.focus` carries the window's own `Window` oid. Rows can outlive their window after a crash, and a row appears before the host registers the window, so srv treats a window as open only while a frontend reports it (#3735).
- **F2 (background mode) has no pane to reopen.** Closing a workspace's last window deletes the workspace and its tabs and blocks (`window_close.rs` → `delete_workspace`). A click in background mode therefore finds no target and opens a plain window, as before, instead of doing nothing. §3.3 D's "reopen the block's own workspace" applies to a workspace that still exists but is shown in no window, e.g. after a window switched workspace.
- **§3.3 D's "re-home the block into a new tab" is not built.** No block outlives its workspace (previous bullet), so there is nothing to re-home.
- **Launcher raise order:** `ShowWindow(SW_RESTORE)` if minimized → `SetForegroundWindow` → host `focus_window` → `FlashWindowEx`. The frontend's `raiseThisWindow` stays as a harmless second attempt.
