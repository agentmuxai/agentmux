# SPEC: MuxBus cloud-relayed login callback (no loopback listener)

**Date:** 2026-08-15
**Status:** Proposed
**Owner request:** "the callback is `http://127.0.0.1:9379/callback?code=...` — can
we keep this managed on the backend? so there isn't a local callback in the browser"
**Prereq context:** PR #2584 (single-flight PKCE login) fixes the immediate 400;
this spec removes the loopback mechanism that made it possible at all.

## 1. Problem

The desktop MuxBus login (`agentmux-srv/src/muxbus/pkce.rs`) uses the RFC 8252
loopback pattern: srv binds `127.0.0.1:9379`, Cognito redirects the browser there,
srv catches the code. Problems, in increasing order of principle:

1. **Fixed-port collisions.** Cognito does exact-string callback matching (no
   wildcard ports), so every instance on the machine shares port 9379. PR #2584
   makes collisions fail cleanly *within* one srv, but two *instances* logging in
   concurrently still race for the port (multi-instance is a first-class AgentMux
   workflow — dev + portable + old build were all running tonight).
2. **The browser touches a localhost URL.** Confusing when it fails (tonight's
   400 was indistinguishable from "the service is broken"), blocked by some
   corporate browser policies/extensions, and it leaks an implementation detail
   into the user-visible flow.
3. **A listening TCP port that exists only sometimes** is an awkward security
   surface (anything local can connect while a login is pending; the state check
   defends correctness, not privacy of the code — though PKCE means a stolen code
   is useless without the verifier).

## 2. Proposed design: cloud-relayed callback with backend polling

Replace the loopback listener with a hosted redirect page plus a short-lived
relay record in agentmux-cloud, keyed by the flow's `state`:

```
srv                        browser                     agentmux-cloud (muxbus API)
 |  POST /login-relay {state, exp≤5m}  ──────────────────────►  create record
 |  open browser → Cognito hosted UI
 |                            | user signs in
 |                            | Cognito 302 → https://muxbus.agentmux.ai/desktop-callback?code&state
 |                            | page POSTs {code, state} to relay, shows
 |                            |   "Connected — return to AgentMux"
 |  GET /login-relay/{state}  ──── poll (1s, ≤5m) ───────────►  {code} (single-read,
 |                                                              record deleted on read)
 |  /oauth2/token exchange with code + PKCE verifier (unchanged)
```

Key properties:

- **PKCE still carries the security.** The relay never sees tokens, only the
  one-time authorization code, which is useless without the `code_verifier` that
  never leaves srv. A hostile reader of the relay gains nothing (and single-read
  + TTL narrows even that).
- **`state` doubles as the relay key.** It is a per-flow UUID generated by srv;
  no new identifier or session concept needed. The relay record is
  create-once/read-once/expire.
- **No local listener, no fixed port, no cross-instance collision.** Each flow
  polls its own key; any number of instances can log in concurrently.
- **One Cognito callback URL forever:** `https://muxbus.agentmux.ai/desktop-callback`
  (replaces `http://127.0.0.1:9379/callback` in the app client's allowed
  callbacks after a deprecation overlap — keep both registered until the last
  loopback build ages out).

## 3. Scope of changes

| Where | What |
|---|---|
| agentmux-cloud | `POST /login-relay` (create, from srv, unauthenticated-but-rate-limited — the record is opaque), `POST /desktop-callback-submit` (from the hosted page), `GET /login-relay/{state}` (single-read delete). DynamoDB item with TTL ≤ 5 min. Static `desktop-callback` page (no JS framework needed — one form-POST + message). CDK: Cognito app-client callback-URL update. |
| agentmux (this repo) | `pkce.rs`: replace steps 4 & 7 (bind + accept loop) with relay create + poll loop. Everything else (verifier, challenge, state, token exchange, credential save) unchanged. Delete `try_bind_callback_listener` and the 400/404 HTML responses. |
| Rollout | Ship cloud first (both callback URLs registered), then the desktop change; loopback path deleted one release later. |

## 4. Alternatives considered

- **Custom URI scheme (`agentmux://callback`).** No listener, but multi-instance
  routing is *worse* (which instance receives the OS-level scheme activation is
  ambiguous — exactly the launcher single-instance-pipe problem again), and
  scheme registration differs per-OS and per-install-mode (portable builds can't
  reliably register). Rejected.
- **OAuth device authorization grant.** The natural "backend-managed" flow, but
  Cognito user pools do not support it natively; faking it via a custom
  authorizer is strictly more cloud surface than the relay above for the same UX.
  Rejected.
- **Do nothing beyond #2584.** Leaves cross-instance port races and the
  browser-visible localhost hop. Rejected by owner request.

## 5. Open questions

1. Rate-limit/abuse posture for the unauthenticated relay endpoints (suggest:
   per-IP token bucket + 512-byte body cap; records are opaque UUIDs).
2. Should the hosted page auto-close (`window.close()` works only for
   script-opened tabs — likely just show "return to AgentMux").
3. Telemetry: count relay creates/completions to watch for the flow silently
   breaking again (tonight's failure mode was *silence*).
