## 3. (b) Getting the browser in on localhost (S1: the one new security piece), revision 3

**Requirement:** another local user, or any local process, can reach a loopback port, so the UI needs a sign-in; and the key must not sit in a URL, in history, in a page, on screen, or in any process's arguments.

**What changed since revision 1.** (Rev 2) A cookie set for `127.0.0.1` is not tied to a port: the browser sends it to every server on that address, and a page from another port can overwrite it. So the cookie is paired with a per-tab token that the browser does isolate by origin. (Rev 3, from AgentY's read) The one-time code must not reach the process list; no failure count may lock the person out; the pair is one session, and the few routes that take the cookie alone are an explicit list.

**Recommendation: srv serves the UI itself and signs the browser in with a one-time code, a confirm step, a cookie and a per-tab token** (not a `serve.mjs`-style proxy; see "The key-adding proxy" below).

1. `agentmux-srv --headless --frontend-dir ...` (the package's `start`) serves the UI on `127.0.0.1:<port>`. The UI files load without a credential (they hold none); every other route is classed in step 5.
2. `agentmux open` (a command-line client run by the same user) reads the key file (owner-only) and the port srv wrote beside it (`<key file>.port`; `--port` overrides), and **never sends the key** (task #2543, agentmux #7177): it sends a fresh nonce to `POST /auth/hello`, srv answers with its own nonce and a MAC made with the key over both nonces, the address srv is bound to and the one other origin it declares, and `open` checks that MAC against the address it is talking to (and the one it will open the browser at) before anything else, so a listener without the key or a forwarder on another port gets nothing reusable and `open` stops with a plain line. Every later request to `/auth/code`, `/auth/pending`, `/auth/confirm` and `/auth/logout` carries a rising number and a MAC of its method, path and body under a key made from the key and both nonces; each answer carries a MAC `open` checks. Through that channel it calls `POST /auth/code` and gets a code: 256 random bits, **single use, 60-second life**. It hands the browser `http://127.0.0.1:<port>/auth/enter#<code>` (the code in the fragment: never in a request line, a server log or a `Referer`), or with `--print` prints that line to the person's own terminal.
3. **The confirm step (R1).** The code is in the launcher's and the browser's arguments, and on a shared Linux box another user reads those from `/proc` and can enter first. A single-use code then goes to the wrong person, so the code alone never makes a live session:
   - `/auth/enter` posts the code and srv makes a **pending** session: it holds no access. The page shows two short words (a check phrase, e.g. `maple-river`, from a 1024-word list, so about 20 bits) and waits.
   - `agentmux open`, still running in the person's terminal, asks srv (with the key) for the pending session and prints: `A browser entered with "maple-river". Is that the page you opened? [y/N]`. On `y` it activates that session; on `n`, on 60 seconds with no answer, or on Ctrl-C it discards it. There is no `--yes` for this step: it is a person at the terminal looking at the browser.
   - **The pending session belongs to the code `open` minted.** `open` can confirm only the session made from that one code, never a session it finds by looking. **How the waiting page gets its answer:** the `/auth/enter` POST returns a **pending handle** (256 random bits, kept in srv's memory only, never in storage, a URL or a log); the page waits on it (a long poll on the handle, same-origin); when `open` confirms, srv hands the cookie and the token to the page **exactly once** on that wait, and the handle is spent; on `n`, on 60 seconds, or on Ctrl-C the handle dies and the wait answers the generic refusal.
   - **The prompt:** the default is **N**; a bare Enter discards. The page shows the phrase large, with one line telling the person to compare it with the terminal and to answer `y` only if they match.
   - If another user entered first with the code from the process list, the person's own browser is refused ("not accepted", the code is used) and shows no phrase, while `open` shows the other session's phrase: the person answers `n`, the session is discarded, and the entry is logged. An attacker cannot make the person's browser show a matching phrase, because the person's browser never got a session.
   - **Why this and not a forwarding file** (an owner-only HTML file in the runtime dir that redirects to `/auth/enter#code`): the file keeps the code out of the arguments, but it only works where the browser can read that folder (a snap-confined browser often cannot), it does nothing when the line is printed or copied to a browser on another machine (the tunnel case, where the line sits in terminal scrollback and in a shared tmux), and it leaves the code on disk. The confirm step covers all three, needs nothing from the browser or the file system, and costs one keypress.
4. **The page and what it holds.** Before posting, `/auth/enter` replaces its history entry (`location.replace` to the same path without the fragment), so the code is not in history. The post is same-origin and srv requires `Sec-Fetch-Site: same-origin` on that POST (the GET of the page itself arrives with `none` when the browser is launched from outside, and serves a page that holds no secret). When `open` confirms, srv gives the page, for **one session**: (i) a `Set-Cookie` named per instance (`amx-s-<instance id>`), `HttpOnly`, `SameSite=Strict`, `Path=/`, no `Secure` on loopback; and (ii) a **session token** (256 random bits) that the page script keeps in `sessionStorage` only (origin-isolated, port included; per tab; unreadable by any other page). The page then navigates to `/`.
5. **The pair is one session, and two classes of route (R3).** srv stores one record per session holding the hash of the cookie value and the hash of the token. It accepts a request only when the cookie **and** the token both name that record: a cookie written from another port (the same cookie name, another session) fails against this page's token instead of mixing with it.
   - **Both required** for every API route, every route that changes state, and the `/ws` upgrade (the token travels as `X-AM-Session` on a fetch and as the `Sec-WebSocket-Protocol` value on a WebSocket, because a browser cannot add a header to one; srv selects a fixed protocol name, never echoes the token, and logs no request headers).
   - **Cookie alone** is allowed only on an explicit allow-list, `COOKIE_ONLY_ROUTES`, in srv: routes that are `GET`, change nothing, and serve a stored file by URL for the page to show or download (attachments, images, downloads; the exact routes are written in S1 from the route table). Each such request must also carry `Sec-Fetch-Site: same-origin` exactly; a missing header, `none`, `same-site` and `cross-site` are refused.
   - **A test walks the route table** and fails on any route that is in neither class: each route is declared `Both` or `CookieOnly` where it is registered, with no default, so a new route cannot be added unclassed.
6. Sessions: 12 hours sliding, revocable (`agentmux logout` revokes all; all die when srv restarts or the key rotates). A request must also have `Host` equal to the one allowed host, and `Origin` (where sent) equal to srv's own origin (next two points); the `/ws` upgrade gets the same checks.
7. Nothing prints the key; nothing puts it in a URL; the browser never holds it. An agent's shell inside the server already holds the key (`pane_env.rs`, said in the headless spec), so the session pair widens nothing for them.

**One canonical host name: `127.0.0.1`.** `localhost` and `127.0.0.1` are two origins to a browser and `localhost` goes through a resolver. srv binds `127.0.0.1` only and accepts only `Host: 127.0.0.1:<its port>` (or the declared origin below). Every URL the commands print uses it. Any other `Host` (`localhost:<port>`, a rebinding name, none) gets the generic refusal below, not a redirect. The `/ws` `Origin` check is the same exact string comparison.

**The `ssh -L` tunnel case (a person reaching a server on another machine).** The browser then sees `http://127.0.0.1:8080` while srv is on `<port>`, so `Host` and `Origin` differ from the canonical ones. Two ways, both an exact match and neither a wildcard:
- **Same port at both ends:** `ssh -L <port>:127.0.0.1:<port> server`, and the browser opens the printed `http://127.0.0.1:<port>/...`. Nothing to declare. This is what `agentmux open` prints on a remote box.
- **A declared origin (R4):** `agentmux config set public-origin http://127.0.0.1:8080` (or `--public-origin` on `start`): **one** string, and it must be `http://127.0.0.1:<port>`. srv refuses to start with any other value: a real host name, `localhost`, an IPv6 or LAN address, and `https` of any host. It then accepts exactly that `Host` and `Origin` in place of the canonical ones (scheme, host and port compared as strings, one entry, no suffix match), and `agentmux open` prints that URL. So the declared origin only moves the port. A reverse proxy in front (a Secure cookie, forwarded headers, the proxy logging `Sec-WebSocket-Protocol`, the refusal reachable from a network) needs its own design and is not in the first package; no untested path ships allowed.

**Failure answers: one generic refusal, a small delay, no lockout (R2).** `POST /auth/code` and `POST /auth/enter` answer every failure the same way: status 403, body `not accepted`, the same headers, whether the code was wrong, expired or used, the `Host`, `Origin` or `Sec-Fetch-Site` was wrong, or the key was wrong. A **valid key on `/auth/code` and a valid code on `/auth/enter` are always accepted**, however many failures came before. No count blocks anything: with 256 bits, single use and 60 seconds, a back-off buys nothing and would let any local process keep the person out. Failures only wait a small fixed delay (250 ms, an async sleep, the same for every kind of failure) before they answer, and at most 64 delayed failures are in flight at once; beyond that a failure answers at once with the same refusal. The success path never shares that queue. srv logs a failed entry as one line: time, route, the remote port, a reason class for the log only (`code`, `host`, `origin`, `fetch-site`, `key`), and the failures in the last minute as a number; never the code, any part of it, the token or a header value. A discarded pending session (step 3) is logged the same way.

**Response headers and the policy of the served UI (R5).** Both auth answers (and the `/auth/enter` page) carry `Cache-Control: no-store`. The UI and the auth page carry `Content-Security-Policy: frame-ancestors 'none'` as part of the policy below, and `X-Frame-Options: DENY` for browsers that read only that. The served UI carries a Content-Security-Policy as tight as the build allows; S1 starts from this and loosens a directive only with a named reason, which it records in this table:

```
default-src 'none'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:;
font-src 'self' data:; connect-src 'self' ws://127.0.0.1:<port>; worker-src 'self' blob:;
object-src 'none'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'
```

`style-src 'unsafe-inline'` is the one loosening I expect (inline styles in the terminal and layout code); S1 measures what else the web build needs (workers, wasm, inline scripts) and removes the `'unsafe-inline'` if it can. A declared origin is added to `connect-src` as its `ws://` form.

**The key-adding proxy (Clamk's note, and why this decision matters).** The development proxy the cloud's `web/dev/serve.mjs` uses adds `X-AuthKey` to every request. Behind it the page has srv's **full** access, with no sign-in of its own: whoever can reach the proxy's port is, in effect, the key. That is acceptable for one developer on a loopback port and nothing else, which is why this design does not use it: the package ships no key-adding proxy, `serve.mjs` stays a development tool (its header should say it must bind loopback only and is not a sign-in), and the localhost sign-in above is what makes a browser's access a decision the person made with `agentmux open`.

What it does **not** defend, said plainly: a process running as the same user can read the key file anyway; a malicious extension in the person's own browser; a person who answers `y` without looking at the phrase; **a listener on the same address and port as srv** (it can pass the hello on and read the one-time code out of the proved answer, because answers are authenticated, not hidden): the operating system refuses that bind to another user on Linux and on Windows by default, so the design assumes it and does not encrypt the channel (AgentY, 2026-11-13). Two things follow from the hello asking for no secret (#7177): a key srv did not generate must be at least 32 characters when srv serves its own UI (a MAC under a short key could be guessed offline), and a flood of hellos replaces channels that proved nothing first, never one that has proved a request. **A nuisance it does not stop:** another local user who reads the code from the process list can keep entering first, so the person is refused each time. They gain no access (the person answers `n`), but it costs the person attempts. When `open` discards a session on `n`, or sees that its code was used and nothing was confirmed, it says so in one line and names `agentmux open --print`: the person pastes the printed line into their own browser, so nothing is in any process's arguments. **Windows:** `0600` means nothing there; the key file needs an owner-only ACL (S1 adds it), today's data-dir lock is not exclusive on Windows (section 5), and a Windows srv started with an empty environment (`env -i`, a service, a CI step) needs `SYSTEMDRIVE` passed: without it srv creates a literal `%SystemDrive%` folder in its working directory (task #2524, to fix in srv; the package's `start` passes the variable meanwhile).

Later convenience, not in S1: handing the token to a new tab of the same origin (a `BroadcastChannel` is origin-bound), so a second tab need not run `agentmux open` again.

Alternative considered: a proxy (`serve.mjs`) in front. It works today, but it holds the key in a long-lived second process, needs its own port and lifecycle, gives the page full access with no sign-in, and cannot do per-session revocation; kept as a development tool only.

## 4. Package, install and release wiring (S3)

- **Contents** (all three already build without CEF for the container image): `agentmux-srv`, `agentmux-mcp`, `agentmux-bashwrap`, the built web UI (`dist/web`), and the `agentmux` command (section 4.1). It does not bundle node; agent CLIs are installed by srv as today (npm). A container image variant already exists (`Dockerfile.srv`).
- **Install:** a release tarball per OS and architecture (`linux-x64`, `linux-arm64`, `macos-arm64`, `macos-x64`; Windows follows the lock work) with a checksum file, and an install script that fetches the right one into `~/.agentmux/server/<version>` and links `agentmux`. `deb`/`brew`/npm are later; the first is the tarball plus script, which is what the container image does.

### 4.1 The `agentmux` command and the setup wizard

One command, subcommands, a short `--help` each; every subcommand that a script may call has `--json` output and exit codes (`0` ok, `1` the thing asked is not so, `2` bad use, `3` could not do it). Nothing prints a key, a code or a token except `open`'s one-time line.

| Command | What it does |
|---|---|
| `agentmux setup` | The wizard (below). Re-runnable: it shows the current choices and changes only what the person changes. |
| `agentmux doctor` | Checks and says what to do: OS and architecture supported; data and install folders writable; the port free; the key file owner-only; `node`/`npm`/`git` present (agent CLIs are installed by srv through npm); the installed version matches the running one; the service unit present and pointing at this install; disk space. Each line is `ok`, `warn` or `fail` with the fix. Exit `1` on any `fail`. |
| `agentmux start` / `stop` / `restart` | Start or stop the server (through the service when one is installed). `start` passes the environment srv needs (`SYSTEMDRIVE` on Windows, `HOME`, the channel). |
| `agentmux status` | Running or not, pid, version, channel, data folder, the one URL, uptime, service state, signed-in browser sessions (a count). `--json`. |
| `agentmux open` | The one-time sign-in line of section 3, opened in the default browser or printed with `--print`; it then stays running to show the check phrase and ask `[y/N]` (section 3, step 3). Needs a terminal. |
| `agentmux logout` | Revokes every browser session. |
| `agentmux logs` | The server's log files: `-f` to follow, `--lines N`, `--since 1h`. The same lines the desktop's logs hold, with the sign-in failures of section 3. |
| `agentmux update` | `--check` says what is newer; plain `update` fetches the release's tarball, **verifies the checksum**, swaps the install folder, restarts, and keeps the previous version for `--rollback`. `--version X` pins. |
| `agentmux uninstall` | Stops the server, removes the service unit and the install folder and the `agentmux` link. **Keeps the channel's data** unless `--purge-data` (interactive: type the channel name; non-interactive: `--purge-data --yes`). It never touches `~/.agentmux/shared` (provider sign-ins and transcripts, shared with a desktop on the same user). |
| `agentmux version` | The version, the commit, the channel. |

**The wizard (`agentmux setup`), in order:** (1) run `doctor` and stop on a `fail`; (2) channel (default `headless`) and the port (a fixed default chosen in S2, shown, changeable); (3) secret store: the file store (default) or the OS keychain, with the consequence of section 5 said in one sentence; (4) install the service (a systemd **user** unit on Linux, a launchd agent on macOS) so it starts at login, yes or no; (5) start it and offer `open`; (6) tell the person how to sign in to a model provider (the agent CLI's own login, in a terminal pane) and where Global Memory, tasks and agents will live. Nothing in the wizard needs the operator's participation.

**Non-interactive:** every question has a flag and `--yes` accepts the defaults, so a script or a container build runs `agentmux setup --yes --channel headless --port 7380 --secret-store file --service --no-open`. Flags: `--yes`, `--channel`, `--port`, `--secret-store file|keychain`, `--service` / `--no-service`, `--no-start`, `--no-open`, `--public-origin http://127.0.0.1:<port>` (section 3), `--install-dir`, `--json`. With no TTY and no `--yes`, setup refuses and says so, rather than guess.

**Service files.** Linux: `~/.config/systemd/user/agentmux.service` (`Restart=on-failure`, the environment above, `loginctl enable-linger` offered, not forced, for a server with no login). macOS: `~/Library/LaunchAgents/ai.agentmux.server.plist`. Both are written from a template that `uninstall` and `doctor` also read. Windows is not in the first package.

**First package versus later.**
- **First (S2 + S3):** Linux x64/arm64 and macOS arm64/x64; the tarball plus install script; `setup`, `doctor`, `start`, `stop`, `restart`, `status`, `open`, `logout`, `logs`, `update`, `uninstall`, `version`; the systemd user unit and launchd agent; no Browser pane (section 7); loopback only.
- **Later:** Windows (after the exclusive data-dir lock and the `SYSTEMDRIVE` fix, with a scheduled-task service); `deb`, `brew`, npm; a reverse proxy in front with TLS (its own design, section 3); `agentmux update` on a schedule; S4.

## 5. The `headless` channel (answering AgentY's question)

**Yes, it should be the package's default.** Facts: `RuntimeMode::current` ends at `Installed` for a binary that is not in a dev tree and has no portable marker, so an installed headless srv resolves the same data dir as a desktop install: `~/.agentmux/channels/stable/versions/<v>/data/` (`data_paths.rs`). `acquire_data_dir_lock` is an advisory `flock` on that dir: it refuses a second srv on Linux and macOS, and **does not exclude on Windows** (its own comment: "not exclusive elsewhere"). Two srvs would open the same SQLite databases there. A channel name of its own (`AGENTMUX_CHANNEL=headless`; the name is not in the reserved list) gives it its own `channels/headless/` tree, its own lock and its own ports, so it can run beside a desktop.

What a separate channel means for the person:
- **Separate (per channel):** its agents (`channels/headless/agents/`), settings (`channels/headless/config/`), and the databases (tasks, history, panes, Global Memory as stored in the data dir; I will confirm the exact location of Global Memory and Kanban in S2 with a test that opens both channels). A person starts with an empty AgentMux there.
- **Shared by default:** provider logins and conversation transcripts (`~/.agentmux/shared/identities/`, `SPEC_SHARED_AUTH_ACROSS_CHANNELS_2026_10_03.md`), so Claude/Codex sign-ins done on the desktop are usable there.
- **Not shared, and that is the catch:** secrets. The desktop keeps Armory keys, connected accounts, the MuxBus (AgentMux Cloud) sign-in and browser-pane logins in the OS keychain; headless defaults to the file store (`shared/secrets/`). So the headless channel starts without them: connect GitHub, add keys and sign in to the cloud again there. `--secret-store keychain` reads the desktop's entries on a machine that has a keychain (a laptop, not a server). Not copying secrets across is deliberate.
- The cloud subscriber is off by default in headless, so the headless server does not appear in the person's cloud presence until they turn it on.

## 6. S4: "the same agents as my desktop, in a browser" is a different feature

It would be the desktop's own srv serving the web UI on its loopback (an opt-in setting, off by default), with S1's sign-in, so the browser is another window onto the same state (the UI already supports several clients on one srv). Needs: the setting, `--frontend-dir`-style serving in a launcher-started srv (today headless-only), the Host/Origin checks, and the browser's gaps below. It does not need a new channel. I would not build it before S1 ships.

## 7. (c) What "the normal experience" lacks in a browser today (`HostCaps` off) and the cost to close each

| Capability | In a browser today | To close |
|---|---|---|
