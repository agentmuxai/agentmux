# Spec: search the agent pane, with a magnifier in the header, a dim mode and stepping through matches

**Task:** #27381 (spec); the build is a follow-on task that starts when the operator approves this.
**Asked by the operator (2026-11-06), in their words:** "lets also add a search for the agent pane, it can be a magnifying glass between the grip and minimize button in the pane header. have it enter a dim mode where only the focused items are undimmed, and as you type into the input box, the search results are undimmed and it lets the user scroll through. since this is virtualized oin the UI, we'd need some sophistiacted workings, lets research latest best practices".
**Author:** Agent1@narko. **Read on:** `origin/main` (2026-11-06), AgentMux 0.60.x. Builds on #6579 (Ctrl+F opens the hidden run that holds a match), `AgentSearchBar`, `useInSessionSearch` and `search-reveal.ts`.
**Status:** active. Approved by the operator 2026-11-07 (all nine decisions as recommended). Build PR 1 (the index, the sliced pass, the settled jump) is in review; PRs 2 to 4 are not started.

## 1. In one paragraph

The pane already has a find bar (Ctrl+F). It matches a row if the row's text contains the query, steps from row to row and flashes the row it lands on. What it does not do is what the operator asked for: there is no header button, nothing says which words matched, nothing dims the rest, the count and the jump are only as good as the row-height estimates (a far jump can land short until rows are measured), every keystroke rescans the whole document on the main thread, and a message that arrives while you search is not folded into the results. This spec keeps the existing bar and its Ctrl+F, adds a magnifier to the header, adds a dim mode that leaves the matching rows at full strength, and adds the workings the virtualised list needs: an incremental index over the data model (never the DOM), a jump that settles on the target after rows are measured, and text highlights painted without touching the rows' markup. It recommends stepping and counting by row ("3 of 41 messages") and painting every occurrence inside the rows that are on screen.

## 2. What exists today (verified in the code, 2026-11-06)

- **Index** (`hooks/useInSessionSearch.ts`): a pass over `paneModel.document()` on every input event, no debounce. A node's text is: markdown `content` (thinking included), user and agent `message`, a tool's name plus `JSON.stringify(params)`, a shell's `cmd` and `title`, a jekt's `from`, `to` and `message`, a system note's `text`; every other kind is empty. Case-insensitive substring (`toLowerCase().includes`); no regex, no word or case options. The result is the matching node ids in document order; `next` and `prev` wrap around and call `jumpTo`.
- **Reveal** (`search-reveal.ts`, #6579): a jump to a node inside an unopened `hidden_run` pins the run, waits two frames for layout, then jumps; `release()` unpins the runs search opened. A stale wait is dropped by a counter.
- **Jump** (`hooks/useScrollToNode.ts`, `virtualization/AgentDocumentVirtualList.tsx` around the `scrollCommand` effect): finds the row by `data-node-id`, centres it, writes the position through `scrollTranscriptTo` (the one scroll writer). Rows outside the rendered window are only an estimate until they mount and the ResizeObserver measures them, and nothing re-aims the jump afterwards.
- **Highlight** (`DocumentRow.tsx`, `styles/_search.scss`): the current row gets `agent-node-search-match` (accent background, a 3 px accent border, a short flash on `--duration-moderate`). The match itself is not marked inside the row; no `CSS.highlights` anywhere.
- **Where it lives:** Ctrl+F toggles the bar (`hooks/useAgentKeyboard.ts`); the bar is a sticky overlay at the top of the pane (`AgentViewOverlays`, `--z-pane-search-bar`). Search keeps the virtualiser from recycling rows while the bar is open (`useInSessionSearch.test.ts`).
- **Header:** the pane header is `PaneGrip` on the left and the end icons on the right (`block/blockframe.tsx`); the end icons are the view's `endIconButtons()` followed by a separator and the minimize button. The agent view returns none today (`agent-model.ts`, `this.endIconButtons = () => []`); the terminal view shows the pattern (`termViewModel.ts`: a list of `{ elemtype: "iconbutton", icon, click, title }`). A magnifier in that list is the first button after the grip's side and before minimize, which is where the operator pointed.
- **Motion:** `app/motion/motion.ts` owns the tiers and categories; `MOTION_POLICY` is empty today, so every category runs in every tier, and durations come from the `--duration-*` tokens, which the animation setting scales (0 when Animations is off). The search flash uses those tokens.
- **Limit that matters:** the search sees the nodes the pane has loaded (the recent slice of history plus what has streamed since), not the whole stored history. Older history loads in pages (`Load older`).
- **Known oddity (Maricon, #6579 check):** a run opened by search is not re-evaluated on every keystroke (a run whose match goes away stays open until the bar closes). The reveal set below is recomputed from the match set on each query change, which closes that.

## 3. Research: what current practice says

Findings from primary sources read on 2026-11-06. Where a claim could not be checked it says so.

1. **Search the data, not the DOM.** VS Code's editor find asks the text model for matches (`model.findMatches`, capped at 19,999) and decorates them ([findModel.ts](https://github.com/microsoft/vscode/blob/main/src/vs/editor/contrib/find/browser/findModel.ts)). Above 1,000 matches it stops drawing a mark per match on the overview ruler and merges nearby ones, to avoid freezes ([findDecorations.ts](https://github.com/microsoft/vscode/blob/main/src/vs/editor/contrib/find/browser/findDecorations.ts)). The terminal uses xterm.js's SearchAddon over buffer lines, with a highlight limit (VS Code sets 20,000, the addon's default is 1,000) and a 200 ms debounce when the buffer changes ([xtermTerminal.ts](https://github.com/microsoft/vscode/blob/main/src/vs/workbench/contrib/terminal/browser/xterm/xtermTerminal.ts), [SearchAddon.ts](https://github.com/xtermjs/xterm.js/blob/master/addons/addon-search/src/SearchAddon.ts)). Not verified: how VS Code limits decorations to the viewport.
2. **The browser's own find cannot see rows that are not mounted.** Two common answers: intercept Ctrl+F and search the data (what this spec does), or keep placeholder rows findable with `hidden="until-found"` (`beforematch` reveals them). Bluesky's virtualised web list does the second ([PR #12067](https://github.com/bluesky-social/social-app/pull/12067)); Chrome documents it ([hidden=until-found](https://developer.chrome.com/docs/css-ui/hidden-until-found)). It cannot be the search engine here, because rows that were never mounted have no text yet, as that PR says itself; it is only a possible bonus for collapsed bodies. Not verified: the Ctrl+F interception claim has no primary source.
3. **Scrolling to an index whose row is not measured lands wrong, and every library says so.** TanStack Virtual takes `align` and `behavior` and tells you to set `estimateSize` generously; smooth scrolling with dynamic sizes measures only items near the target; `cancelScroll` stops corrections when the user scrolls ([Virtualizer API](https://tanstack.com/virtual/latest/docs/api/virtualizer)); a reported bug has `scrollToIndex(last, { align: "end" })` stopping short on a stale cached size ([issue #1290](https://github.com/TanStack/virtual/issues/1290)). react-virtuoso lands wrong on unmeasured rows ([#1447](https://github.com/petyosi/react-virtuoso/issues/1447)), its own retry can undo a user's scroll in the first ~150 ms ([#1550](https://github.com/petyosi/react-virtuoso/issues/1550)), and a retry loop of your own on top of its retry bounces ([#1503](https://github.com/petyosi/react-virtuoso/issues/1503)). No primary source prescribes the loop; the pattern assembled from these is: jump without smooth scrolling, re-aim after measurement settles, abort on any user scroll, and own the loop in one place. Our list is our own virtualiser, so the loop is ours to write and to keep in the one scroll writer.
4. **Highlight text without changing the DOM: the CSS Custom Highlight API** (`CSS.highlights`, `Highlight`, `::highlight()`). Support: Chrome and Edge 105+, Safari 17.2+, Firefox 140+, Baseline 2025 ([caniuse](https://caniuse.com/mdn-api_highlight), [MDN](https://developer.mozilla.org/en-US/docs/Web/API/CSS_Custom_Highlight_API)). Styling is limited to colour, background and a few text properties; ranges break if the DOM changes between building and registering them; guides advise capping the count and adding ranges one at a time ([SitePoint](https://www.sitepoint.com/css-custom-highlight-api-javascript-guide/)). No rigorous benchmark at thousands of ranges was found. **Resolved from the version pin:** the release workflow pins CEF at Chromium 148 (148.0.7778.180; `.github/workflows/release-core.yml`, `docs/analysis/REPORT_CEF148_FORK_UPDATE_2026-06-02.md`), and the older 146 pin is also past 105, so the API is there. The code still feature-checks `CSS.highlights` and falls back.
5. **Keep the work off the long-task path.** Tasks over 50 ms are long tasks; yield about every 50 ms with `scheduler.yield()` and fall back to `setTimeout(0)` ([web.dev](https://web.dev/articles/optimize-long-tasks)); `scheduler.yield` is Chrome and Edge 129+, Firefox 142+, not Safari ([caniuse](https://caniuse.com/mdn-api_scheduler_yield)). No V8 benchmark was found for `indexOf`, `toLowerCase` or `normalize("NFD")` over tens of MB; the honest position is that each is one pass and one allocation, so fold once per node and cache, and measure in our own runtime if the first build feels slow (§9).
6. **Jump-to-message and context.** Discord's API has an `around` parameter to fetch messages around an id ([docs](https://docs.discord.com/developers/resources/message)). No engineering write-up of Slack or Discord's client virtualisation or of how highlight state survives recycling was found, so this spec does not claim to copy them; the rule used is the obvious one: state is keyed by node id, never by a DOM node.
7. **Dimming everything but the matches** has precedents (fzf's raw mode dims non-matches; Firefox's `findbar.modalHighlight` dims the page, [Bugzilla 384458](https://bugzilla.mozilla.org/show_bug.cgi?id=384458)) but no first-party example in a chat product was found. Accessibility rules that apply: WCAG 1.4.3 (4.5:1 for normal text; only inactive controls are exempt, so dimmed content still has to read), 1.4.11 (3:1 for state and focus indicators), and an always-present `aria-live="polite"` region for "N of M" ([1.4.3](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html), [1.4.11](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html), [aria-live](https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Attributes/aria-live)). Not verified: sources for `role=search` and for reduced-motion handling (this repo's own motion policy governs the latter).

**What to take, for our case:** search a store keyed by node id; fold text once per node and cache it; index incrementally; yield about every 50 ms and cancel a pass when the query changes; cap and degrade like VS Code; paint matches with `CSS.highlights` and a `<mark>`-free fallback; settle the jump after measurement and abort on a user scroll; reveal collapsed content by id; dim as a mode, not the default; keep dimmed text readable; announce the count politely.

## 4. Design

### 4.1 The UI

- **Magnifier:** an icon button (`magnifying-glass`, tooltip "Find in conversation", with the shortcut) as the first of the agent view's `endIconButtons`, so it sits on the right of the header, left of the separator and the minimize button. It is a toggle: pressed while the bar is open. The state lives in the pane (`input.search`), so the model exposes `searchOpen` and `toggleSearch` to the header the way it already bridges `progressBarMount`.
- **The bar:** unchanged in place (a sticky overlay at the top of the pane) and in what it already does. It gains: the count as "3 of 41" (rows, §4.2; "No matches" when empty), previous and next buttons, a close button, and a dim switch (§4.4). Keys: Enter and F3 next, Shift+Enter and Shift+F3 previous, Esc closes and returns focus to the magnifier, Ctrl or Cmd+F opens and focuses it (or selects its text when it is already open). Arrows are not bound while the text field has focus, because they move the caret.
- **One open path:** the magnifier, Ctrl+F and the command palette ("Find in conversation") open the same bar; nothing else is added.

### 4.2 What a match is and how the index works

- **Item = a row.** The count and the stepping are by row: a message, a tool call, a shell, a jekt, a note, a thinking block. A row with five occurrences is one stop. Reason: the index is made from the data, and the rendered text differs from the source text (markdown syntax, a tool's collapsed JSON), so counting occurrences in the data and painting them in the DOM would disagree. Rows agree by construction: a row matches if its searchable text contains the query. Occurrence stepping is a later option (decision 1).
- **Searchable text per row** is today's list (§2) plus attachment file names, and image alt text where it is in the markdown. Tool results are not in the document (they load on demand) and stay out; thinking stays in. One function, `searchableText(node)`, owns the list, so the index, the tests and the highlighter share it.
- **The index** (`search/transcript-index.ts`, new): a map from node id to `{ ref, folded }`, where `ref` is the node object and `folded` is `searchableText(node).toLowerCase()`, capped at 64 KB per row. It is built lazily when the bar first opens (not at ingest: most panes never search), kept while the bar is open and dropped when it closes. A node whose object is unchanged since it was folded is not folded again; a streamed node (the same id, a new object) is refolded alone.
- **A query pass** walks the nodes in document order in slices of about 8 ms, yielding between slices (`scheduler.yield` where it exists, `setTimeout(0)` otherwise), and is cancelled by the next query or by Esc. Keystrokes are debounced by 120 ms; the count shows "Searching…" only if a pass takes over 150 ms. The result is `matchIds: string[]` plus a `Set` for O(1) "does this row match" reads.
- **Where the current match starts:** the first match at or after the top of what is on screen (as VS Code starts from the cursor), not the first in the document. Pressing Enter from there steps forward; the list wraps.
- **Scope:** the nodes the pane has loaded (§2). The bar says so when older history exists: "Searched the last N messages" with a "Load older and continue" action; stepping past the oldest loaded match offers the same (decision 3).
- **Why not a Web Worker:** the document lives in main-thread store objects; copying 10,000+ rows into a worker costs about what the search does, and chunked passes keep each task under the long-task line. A worker is the next step if the measured cost says so (§9).

### 4.3 Jumping to a match in the virtualised list

- **Two phases, one writer.** The scroll controller (`scroll/one-way-flow.ts`, the one scroll writer) gets `settleOnNode(nodeId)`: (1) aim at the node's estimated top with an instant write (no smooth scroll: smooth plus a re-aim is the combination the libraries report as bouncing); (2) as rows mount and the ResizeObserver reports sizes, re-aim whenever the target row's measured top is not where it was aimed, until two consecutive frames agree or 600 ms (about 8 passes) have gone; (3) abort at once on any wheel, touch, key scroll or drag (the user wins), and on a newer jump. The existing smooth centre stays for a jump to a row that is already on screen.
- **Zoom and the scroll slice (AgentX, 2026-11-06):** the settle loop works in unzoomed CSS px, like the layout slice (INV-2 of the agent pane layout reducer): it compares the target's measured top as the slice reports it, never a raw DOM pixel, and is tested at 150% zoom. It never fights the zoom anchor restore (`SPEC_ZOOM_ANCHOR_AND_AUDIT_2026_10_29`): a zoom change, a resize or an anchor restore during a settle aborts the loop exactly as a user scroll does, and search never re-places the scroll on a zoom change itself.
- **One writer, one follow controller:** the settle target is added to the existing transcript-scroll-writer guard (`scripts/check-transcript-scroll-writers.mjs`) as a call into `one-way-flow.ts`, so a second writer cannot appear. The follower is off while a match is current; "jump to bottom" and Esc turn it back on through the same follow controller, with no second flag.
- **Hidden and collapsed content:** unchanged from #6579 and extended: the rows that need opening are the ones holding the current match, pinned by id, and recomputed from the match set at every query or step, so a run whose match is gone closes (the oddity in §2).
- **While the agent writes:** search must not fight the follower. Stepping, or typing a query that jumps, turns follow-the-tail off (as any scroll away from the bottom does); Esc and the existing "jump to bottom" put it back. The follower is never re-enabled by an arriving message while the bar has a current match.

### 4.4 Dim mode and highlights

- **Dim is opacity only (AgentX):** it never changes a row's height or whether it is mounted, so it cannot trigger a re-measure; a test pins that a dim toggle moves no row and mounts or unmounts none. While the bar is in dim mode, a row that is not a match is shown at reduced strength and a matching row at full strength. Implementation: the transcript scroller gets `data-search-dim`; each row reads one boolean from the match `Set` and carries `data-search-match="true|false"`; CSS `[data-search-dim] .agent-row[data-search-match="false"] { opacity: var(--search-dim-opacity); }`. No per-row work beyond that attribute, and rows recycled by the virtualiser get the right state on mount because it comes from the node id, never from the DOM node.
- **What "item" means for dimming:** the whole row, as for the count. A message, a tool call and a jekt are each one item; a matching row is undimmed whole, and the matched words inside it are highlighted (below). The composer, the working row, the bottom panels and the header are never dimmed (they are not transcript items).
- **When it starts** (decision 2): the operator's words are "have it enter a dim mode". The recommendation is that opening the bar does not dim until there is a query, because an all-dim pane with nothing typed shows nothing and reads as broken; the first character dims. It is one line to flip.
- **Dim level and contrast:** `--search-dim-opacity` is chosen per theme as the lowest value, not below 0.5, at which the theme's main text over its background stays at 4.5:1 (WCAG 1.4.3), so a dimmed row is still readable. A test measures every theme, as `pill-colors.test.ts` does for the pills, and fails if a theme cannot reach 4.5:1 at 0.5, in which case that theme's value is raised.
- **Text highlights:** `CSS.highlights` with two highlights, `agent-search` (every occurrence, in the rows that are mounted) and `agent-search-current` (the occurrences inside the current row). A mounted row registers its ranges after render by walking its text nodes (`TreeWalker`) and finding the query in each one with the same fold; it removes them when it unmounts or the query changes. A row with fewer rendered occurrences than the data has (the match is in a collapsed tool's JSON, say) is still counted and still current: the whole row takes the existing current-row treatment, so a count never points at nothing. Where `CSS.highlights` is missing, the fallback is the row treatment alone (no per-word marks), not a DOM rewrite.
- **Colour and shape:** the current row keeps the existing accent background and 3 px left border; occurrences use the accent wash, the current row's occurrences a stronger one. Both come from theme tokens; nothing is colour-only (the current row also has the border and `aria-current`). In forced-colours mode the highlight uses `Highlight` and `HighlightText`, and the border carries the state.
- **Motion:** the dim fades on the existing `--duration-*` and `--ease-*` tokens, which the animation setting scales to 0 when Animations is off; there is no `prefers-reduced-motion` query in the component (the motion policy owns that, `check-motion-gates` checks it). The current-row flash stays as it is.

### 4.5 While the agent is still writing, filters, collapsed runs, images

- **Streaming:** a new row is added to the index when it arrives; a growing row (the streaming message) is refolded after a 200 ms quiet period, alone. The count updates ("3 of 42") without moving the current match (it is held by node id, not by index). New matches below the viewport do not move the view; the count is the notice. A match that appears in the current row's text moves nothing.
- **Verbosity filter** (`agent:view` switches): matches are found in rows the view hides or folds. The current match's row is revealed (opened, or shown if its kind is hidden) while it is current and returned when the step moves on, the same rule as hidden runs. The count includes them (decision 5). In dim mode a revealed row is a match and so full strength.
- **Collapsed runs and tools:** as above, by id.
- **Images:** an image is not searchable; its file name and its alt text are. A row with images dims like any other (the images with it); there is no text recognition.

### 4.6 Accessibility

- The bar is `role="search"` with a labelled input; the count sits in a live region (`aria-live="polite"`) that exists before it changes, updated at most every 400 ms, so typing does not read out every count: "3 of 41", "No matches".
- Focus order: magnifier, then the field (focus moves to it on open), previous, next, dim switch, close. Esc closes and returns focus to the magnifier; focus is never lost to the body. Stepping keeps focus in the field so the next Enter works.
- The current row has `aria-current="location"`; dimming is opacity only (no `aria-hidden`, no `inert`), so assistive technology still reads every row and Tab still reaches links in dimmed rows.
- Contrast: dimmed text 4.5:1 (§4.4, tested per theme); the current-row border and focus ring 3:1 (WCAG 1.4.11).

## 6. Test plan

- **Unit, the index:** `searchableText` per node kind (one test per kind in the list); case-insensitive match; a node unchanged since folding is not folded again (count the folds); a streamed node is refolded alone; the 64 KB cap; ids and order are stable across a document change; the current match is held by id when rows are added before it.
- **Unit, the pass:** it yields between slices (with a fake clock and a fake `scheduler.yield`); the next query cancels the old pass; Esc cancels; a pass over 50,000 synthetic rows of 2 KB finishes with no slice over its budget and without scanning rows twice (these check the algorithm's shape, not wall-clock time).
- **Unit, the jump:** a fake virtualiser whose row heights change as rows mount: the settle loop ends on the target, re-aims when a measurement moves it, stops at 600 ms, and stops at once on a wheel, touch or key event and on a newer jump; no scroll call outside `one-way-flow.ts` (`check-transcript-scroll-writers`).
- **Unit, zoom:** the settle loop at 150% zoom lands on the target in unzoomed px; a zoom change, a resize and an anchor restore each abort it; search never writes a position on a zoom change.
- **Unit, dim:** toggling dim changes no row height and mounts or unmounts no row.
- **Unit, reveal:** a run opened by the current match closes when the match goes away on the next keystroke, and when the step moves on; a run the person opened themselves stays.
- **Component:** the header button toggles the bar and shows pressed; keys (Enter, Shift+Enter, F3, Esc, Ctrl+F); the count text and the live region; focus returns to the magnifier on Esc; the dim attribute follows the query; a row's `data-search-match` follows the node id after a remount.
- **Contrast:** every theme's dimmed main text against its background reaches 4.5:1 at the chosen opacity.
- **No lab run.** Real-transcript timing, a soak and any scripted or real-mouse UI run need the operator's OK first; until then nothing above depends on wall-clock numbers. Look checks on macOS and Linux (the cross-platform rule) are done by Clare and Maricon on the visual PRs, in their own builds; they are not labs.

## 7. What this does not do

- No regex, whole-word or match-case options; no diacritic folding (the fold is `toLowerCase`, as today, the same one in the index and the highlighter); no fuzzy matching.
- No search of tool output (it is not in the document; loading it all would defeat the index), and no text recognition in images.
- No search across panes or agents (the Audit and the History view own those).
- No new store, no change to what the agent reads or to the history file.

## 8. Risks

- **The highlighter walks rendered text.** Markdown renders can split a word across nodes (inline code, emphasis); a match that spans nodes is not painted, though its row is counted and current. Acceptable for a first version; the row border still says where it is.
- **`CSS.highlights`** is in Chromium 105 and later, and our CEF pin is 148 (§3.4), so it is there; the code still checks for it and, if it is missing, falls back to the row treatment alone (no per-word marks).
- **`scheduler.yield`** is in Chromium 129 and later, so it is there at the 148 pin; the code still feature-checks it and falls back to `setTimeout(0)`, slightly slower and not priority-boosted.
- **Memory:** the folded copy roughly doubles the text of the rows it covers while the bar is open; the 64 KB cap per row and dropping the index on close bound it.

## 9. Open decisions for the operator (recommendation first)

1. **What is one stop: a row, or each occurrence?** Recommended: **a row**, counted as "3 of 41 messages", with every occurrence painted on screen. Occurrence stepping can come later; it needs the rendered text to be the searched text.
2. **When does dim start?** Recommended: **from the first character typed**; an open bar with an empty field leaves the pane at full strength. Alternative (your words read this way): dim as soon as the bar opens.
3. **How far back does it search?** Recommended: **the loaded slice, saying so, with "Load older and continue" when you step past the oldest loaded match** (PR 4). Alternatives: loaded slice only; or a query of the stored history (a bigger piece, in the history store's area).
4. **What text is searched?** Recommended: **as today plus file names and image alt text; not tool output.**
5. **Do hidden, folded and collapsed rows count?** Recommended: **yes**, and the current one is opened while you are on it.
6. **How dim?** Recommended: **the lowest level, not below 50%, at which each theme's text still reads at 4.5:1.** Say if you want it stronger and accept lower contrast in light themes.
7. **Ctrl+F in an agent pane** keeps opening this bar rather than the browser's own find. Recommended: **yes**.
8. **Resolved, no lab:** the CEF pin is Chromium 148, which has `CSS.highlights` (105) and `scheduler.yield` (129), so nothing needs measuring to decide the design. The code keeps a feature check and a fallback for each. Real timings on a large transcript are a lab and need the operator's OK first; the build does not depend on them. (AgentY, 2026-11-06.)
9. **Where the bar sits.** Recommended: **keep the sticky top overlay and add the header button to open it**, rather than moving the input into the header, which is too narrow for a field, a count and two buttons.
